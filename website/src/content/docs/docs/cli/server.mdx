Run the control API and scheduler without loading project Python, with its settings in
`server.toml`:

```bash
sqb server --config server.toml
```

## Configure the server

`server.toml` holds the listener, retention, sign-in and the launchers that start workers. The
server reads it once at start-up, so restart the server after you change it:

```toml
[server]
host = "0.0.0.0"
port = 8000
default_role = "viewer"

[retention]
run_log_days = 7

[trusted_proxy]
origin = "https://control.example.com"
trusted_peers = ["10.0.0.5"]

[trusted_proxy.identities]
orders-person = "0190c3c1-5a4e-7b8e-9f00-2a7d1c9e4b11"

[[launchers.docker]]
location = "orders"
target = "development"
server_url = "http://server:8000"
max_workers = 2
socket = "/var/run/docker.sock"
location_container = "orders-location"
executable = "/usr/local/bin/sqb"
```

| Section | Keys |
| --- | --- |
| `[server]` | `host` (default `127.0.0.1`), `port` (`8000`), `database_env` (`SQLBUILD_CONTROL_DATABASE_URL`), `password_origin`, `default_role` (`none`), `scheduler` (`true`), `attention_snooze` (`"24h"`); see [Acknowledge attention items](#acknowledge-attention-items) |
| `[retention]` | `statistics_days`, `audit_days`, `snapshot_count`, `run_log_days`, `run_log_count`, `state_history_versions`, `run_output_days`; see [Set retention](#set-retention) |
| `[output]` | `store` (an `output` folder beside a SQLite control database, or `~/.local/state/sqlbuild/output` with PostgreSQL), `max_bytes_per_run`; see [Keep run output](#keep-run-output) |
| `[oidc]` | `origin`, `issuer`, `client_id`, `identities`, and optionally `client_secret_env`, `certificate_authority`, `groups_claim` and `group_roles` |
| `[trusted_proxy]` | `origin`, and optionally `trusted_peers` (`127.0.0.1` and `::1`), `allowed_hosts`, `username_header` (`X-SQB-User`), `display_name_header`, `email_header`, `unknown_users` (`provision_viewer`), `proxy_logout_url` and `identities`; see [Sign in through a reverse proxy](#sign-in-through-a-reverse-proxy) |
| `[[launchers.docker]]` | `location`, `target`, `server_url`, `max_workers`, `socket`, `location_container`, `executable`, and optional `run` and `pool_caps` tables; see [Limit worker containers](#limit-worker-containers) |
| `[[launchers.local]]` | `location`, `target`, `server_url`, `max_workers`, absolute `project_dir` and `executable` paths, and an optional `pool_caps` table |

- A flag overrides the same setting in the file: `sqb server --config server.toml --port 9000`
  listens on port 9000.
- Keep secrets in environment variables. The file names the variable, as `database_env` and
  `client_secret_env` do, never the secret itself.
- A worker loads its project's [env file](/docs/concepts/project-configuration#env-file) for its
  target when it starts, so provider secrets can live there instead of in the launcher's
  environment. Variables already in that environment win.
- Each launcher names a location by the name you gave `sqb admin create-location`. Create the
  location before you start the server; an unknown name stops it.
- `sqb scheduler --config server.toml` reads the same file for its control database and launchers.
- `sqb admin` doesn't read the file. When `database_env` names another variable, pass the same
  name to `sqb admin --database-env` so it changes the server's store.
- An unknown section or key stops the server with the line it is on.

Use `sqb server --help` for the remaining options.

## Stop the server

SIGINT (Ctrl+C), SIGTERM and SIGHUP, which a closed terminal sends, all stop the server the same
way: it stops scheduling, asks each local worker to stop, waits for the workers to cancel their
statements and record their runs, and releases their claims. Each local worker runs in its own
process group, so Ctrl+C in the server's terminal reaches only the server. A second SIGINT or
SIGTERM while the workers stop kills their process groups at once; the server still records the
runs and releases their claims before it exits.

## Serve over HTTPS

Code locations and workers send their bearer token with every request to the `--server` URL.
`sqb server` serves plain HTTP, so put TLS or an HTTPS reverse proxy in front of it and give
locations and workers its `https://` URL. When a location or worker connects to an `http://` URL
on another host, it prints this warning once and keeps running:

```text
warning: the bearer token for http://control.example.com travels unencrypted over HTTP; put TLS or an HTTPS reverse proxy in front of the server
```

Connections to `localhost`, `127.0.0.1` or `::1` print no warning.

## Add people who sign in with passwords

With `password_origin` set, people sign in with a name and password. Someone with `user.manage`
adds a person from **People → Add person** with their sign-in name, a first password of at least
12 characters and, with `role.assign` as well, a built-in role everywhere. Share the password with
them; they can change it after they sign in. Behind OIDC or a trusted proxy, people appear the
first time they sign in instead, and the button isn't shown.

## Administer the server with sqb admin

`sqb admin` works on the control database directly, on the server's host. Each command prints one
line on stderr that names what it did:

```text
$ sqb admin create-location orders
Registered location orders (01a1fb47-0b3a-7631-ba35-e44d44d072f2)
```

| Command | On stdout |
| --- | --- |
| Issues a token or key: `issue-location-token`, `rotate-token`, `create-service-account`, `rotate-service-account` | Only the secret, once, so `VALUE="$(sqb admin ...)"` captures it. Nothing for an imported key |
| Reads: `location-work`, `list-service-accounts` | Plain rows, with no header |
| Everything else | Nothing |
| Any command with `--json` | Only the JSON result, with the secret in it when one was issued. The line on stderr is left out |

When a script needs an ID, such as the new location's, use `--json`. `--verbose` also says when the
control store opens and is ready; without it, `sqb admin` says so only when opening takes more than
a second, as a migration can. Put both options after the command's name. A command whose output
can't be written exits with status 1 and says the change may already be committed.

## Call the server from scripts with service accounts

A service account lets a script, such as a deploy that republishes a project, call the server
with an API key under its own name. Add one in **People → Service accounts**, or on the server's
host:

```bash
sqb admin create-service-account orders-deploy --role developer --description "Release pipeline"
```

The key is the only thing on stdout (`key` with `--json`), and the UI shows it once in a dialog.
Store it now, for example in your deploy's secret store: it isn't shown again, and the server keeps only a hash of it. The script
sends it in an `Authorization` header:

```bash
curl -H "Authorization: Bearer $SQB_SERVICE_KEY" https://control.example.com/api/control/bootstrap
```

| Command | Does |
| --- | --- |
| `sqb admin create-service-account NAME --role ROLE` | Adds the account with a built-in role everywhere (`viewer`, `operator`, `developer` or `admin`) and prints its key. `--description` says what uses it. |
| `sqb admin rotate-service-account NAME` | Prints a new key. The replaced key stops now, or keeps working for `--overlap-minutes` (at most 1440) while you update the script. |
| `sqb admin disable-service-account NAME` | Refuses every key of the account at once. |
| `sqb admin enable-service-account NAME` | Accepts the same keys again. Rotate as well if a key may have leaked. |
| `sqb admin list-service-accounts` | Lists the accounts, their roles and the prefixes of their working keys, never the keys. |

- **Keys.** A key starts with `sqbk_`, so you can recognise one in a script or a secret scanner.
  The UI and the list show only its first characters, such as `sqbk_Q7m2xT`.
- **Rotating.** One old key works at a time: rotating again stops a key that is still in its
  overlap. **Stop now** in a key's menu stops any key at once, the current one included; the
  account then has no working key until you rotate.
- **Importing a key.** To recreate a control store with the same key, pass
  `--key-from-env VAR` to `create-service-account`, with the key in the environment variable `VAR`.
  It must start with `sqbk_` and have at least 32 more characters, without spaces. Generate it
  randomly, for example `sqbk_` and 40 random letters and digits: SQLBuild can't tell a guessable key
  from a strong one, so an imported key is only as strong as you make it. The command then doesn't print the
  key. Only the CLI imports keys; the UI always makes a new one.
- **Any address.** A keyed request is accepted on whatever address the server listens on, with any
  `Host`, so a server behind a sign-in proxy can also listen on the network, such as
  `host = "0.0.0.0"`, for scripts. The proxy's username header is still trusted only from
  `trusted_peers`, so a direct request can't sign in as a person.
- **TLS.** `sqb server` serves plain HTTP, and a key sent over plain HTTP crosses the network
  unencrypted. Terminate TLS in front of any network listener, as in
  [Serve over HTTPS](#serve-over-https), and give scripts its `https://` URL. The server warns at
  start-up when it accepts keys on an address other than loopback without an `https://` origin.
- **Without people's sign-in.** On a server with no `password_origin`, `[oidc]` or
  `[trusted_proxy]`, service keys are the only way to call its person API. Its sign-in page and
  `sqb login` say so instead of asking for a password, and Settings shows the sign-in as
  service account keys only.
- **Roles.** A service account holds its built-in role everywhere and doesn't get `default_role`.
  That role decides what its key may do, as a person's does: an `admin` key can also manage service
  accounts and roles, though it can't remove or disable the last admin who is a person.
  In the UI, changing it needs `role.assign`.
- **No sign-in.** A service account has no password, browser session or `sqb login`, and a
  `[trusted_proxy.identities]` binding to one is refused.
- **Audit.** Its actions appear in the audit log under its name. A request with a key that the
  account no longer accepts, because the account is disabled or the key was stopped or rotated
  away, is refused and recorded as `service_account.key_refused`, at most once a minute per key.
- **Last used.** The Service accounts tab shows when each key last made a request that wasn't
  refused.

| Action in the UI | Needs |
| --- | --- |
| See service accounts | `user.manage` or `role.assign` |
| Add a service account | `user.manage` and `role.assign` |
| Rotate, stop a key, disable or enable | `user.manage` |
| Change the role | `role.assign` |

## Sign in through a reverse proxy

A reverse proxy such as Apache or nginx can sign people in and tell the server who they are in a
request header. The server trusts that header only on requests whose socket peer is listed in
`trusted_peers`, so it never trusts a header that a browser sends straight to the server. With the
proxy on the same host, bind the server to loopback so that only local processes reach it, or
listen on the network as well when [service accounts](#call-the-server-from-scripts-with-service-accounts)
call it from other hosts:

```toml
[server]
host = "127.0.0.1"
port = 8000

[trusted_proxy]
origin = "https://control.example.com"
username_header = "X-SQB-User"
display_name_header = "X-SQB-Display-Name"
proxy_logout_url = "https://sign-in.example.com/logout"
```

| Key | Meaning |
| --- | --- |
| `origin` | The URL people open, such as `https://control.example.com`. `http://` works too: the server warns at start-up, and `https://` is recommended. |
| `trusted_peers` | The proxy's IP addresses. Without this key the server trusts `127.0.0.1` and `::1`, for a proxy on the same host that connects to `localhost` over either IPv4 or IPv6, so any process on the server's host can send the header and sign in as anyone. Setting `trusted_peers` narrows this to the addresses you list: a proxy on another host, listed by its own address, keeps local processes out. The server takes the peer from the connection, never from `X-Forwarded-For` or `Forwarded`. |
| `allowed_hosts` | Further host names the proxy sends in `Host`, without a scheme or port. A proxy that keeps the browser's host name, such as Apache with `ProxyPreserveHost On`, needs every name people reach the server under. A proxy on another host needs the name or address it forwards to, such as `10.0.0.2`. |
| `username_header` | The header naming the signed-in person, `X-SQB-User` by default. |
| `display_name_header`, `email_header` | Optional headers whose values the UI shows. The server doesn't store them. |
| `unknown_users` | `provision_viewer` (default) gives a person signing in for the first time an account with the `viewer` role; `reject` refuses them. |
| `proxy_logout_url` | Where the UI's **Sign out** link goes. Only the proxy can end its own sign-in, so without this key the UI shows no sign-out link. |
| `[trusted_proxy.identities]` | Optional: binds a username to a principal you already created with `sqb admin create-principal`. |

Turn on the proxy's authentication for every location it forwards to the server, and have the proxy
set every identity header you configured itself. A header the proxy leaves alone passes through
from the browser, so set the username header and set or unset the display name and email headers
on every request. With Apache on the same host,
forwarding port 80 to the server on port 8000:

```apache
<Location "/">
    # Your authentication: AuthType, AuthName, providers and Require valid-user
    RequestHeader set X-SQB-User "expr=%{REMOTE_USER}"
    # Set this from your provider's display name, or unset it when you have none
    RequestHeader unset X-SQB-Display-Name
</Location>
ProxyPass "/" "http://127.0.0.1:8000/"
ProxyPassReverse "/" "http://127.0.0.1:8000/"
```

- **Who can sign in.** Any process that can connect to the server from a trusted peer address can
  sign in as anyone by sending the username header. Keep the server's port reachable only from the
  proxy: bind it to `127.0.0.1` when they share a host, or firewall it.
- **Usernames are case-insensitive.** The server trims and lowercases the username, so `Admin` and
  `admin` are one person; your identity provider must treat them as the same account. A username
  must be 1 to 128 characters of `a`-`z`, `0`-`9`, `.`, `_`, `@`, `+` or `-`, starting with a
  letter or digit. Keys under `[trusted_proxy.identities]` are lowercased too, so no two keys may
  differ only in case.
- **New people.** A provisioned person is named after their username, and an administrator grants
  more roles in the UI. A username that matches another principal's name in any case is refused
  rather than taken over; bind it under `[trusted_proxy.identities]` to sign that person in.
- **Removing people.** `unknown_users = "reject"` stops new people from being provisioned; it
  doesn't remove people already provisioned. Disable a principal to remove their access.
  Removing someone at the proxy doesn't end their `sqb login` sessions: they last until they expire
  or the principal is disabled.
- **Host names.** A request from a trusted peer must carry a `Host` of `127.0.0.1`, `localhost`,
  `[::1]` or the host of `origin`, with any port, or a name in `allowed_hosts`; the server ignores
  `X-Forwarded-Host` here. A proxy on the same host that forwards to `127.0.0.1`, `localhost` or
  `[::1]`, as Apache does by default, needs no `allowed_hosts`. Any other `Host` gets
  `403 Forbidden`, and the server logs it once.
- **Writes.** A browser write is accepted when it carries the `X-SQB-CSRF` header, which the UI
  always sends and which a page on another site cannot send, or when its `Origin` header is exactly
  `origin`. The server allows no cross-origin requests.
- **Finding the proxy's address.** When a request carrying the username header comes from a peer
  that is not in `trusted_peers`, the server ignores the header and logs the peer once, without the
  header's value:

  ```text
  warning: ignored the trusted-proxy username header x-sqb-user from 10.0.0.7, which is not in [trusted_proxy] trusted_peers; if 10.0.0.7 is your proxy, add it there
  ```

- **No browser cookies.** The proxy authenticates every request, so the server issues no session
  cookie to browsers in this mode, over `http://` or `https://`.
- **The CLI.** `sqb login` still needs an `https://` server URL, so that its session token never
  crosses the network unencrypted.
- **Locations and workers.** They use bearer tokens, not the proxy. On the server's own host, give
  them `http://127.0.0.1:8000` so their tokens stay on loopback. Service accounts call with their
  keys too, directly or through the proxy.
- **Streaming.** The live-update feed sends `Cache-Control: no-cache, no-transform`, which stops
  `mod_deflate` from compressing it, and `X-Accel-Buffering: no`. It sends a keep-alive comment
  every 15 seconds, well within Apache's default 60-second `Timeout`. Long work, such as planning a
  build or testing a connection, runs in the background while the UI polls for the result, so no
  browser request waits on it.

`[trusted_proxy]` cannot be combined with `password_origin` or `[oidc]`. The server refuses to
start when they are combined, when `trusted_peers` is an empty list, when the username, display
name and email headers are not distinct, or when one of them is a header that browsers, proxies or
the server set, such as `Cookie`, `Host`, `Origin`, `Via`, `X-Forwarded-For`, `X-Real-IP` or any
`Sec-` header.

To check that streaming passes through the proxy unchanged, sign in through it in a browser, open
the developer tools' Network tab, select a location, and inspect the `changes` request. Its type is
`eventsource`, its response headers include `Cache-Control: no-cache, no-transform` and
`X-Accel-Buffering: no`, and it has no `Content-Encoding`. Its events keep arriving for minutes.

## Receive platform events

Set `SQLBUILD_PLATFORM_WEBHOOK_URL` in the server's environment to have it `POST` each platform
event to that URL as JSON. Leave it unset to turn delivery off. Locations and workers never
receive the URL.

```json
{
  "storage_id": 4182,
  "event_id": "01a1d3c2-6f0e-7a51-9b2e-3c4d5e6f7a80",
  "occurred_at": "2026-11-13T07:12:04.381Z",
  "payload": {
    "platform": {
      "kind": "run_failed",
      "run_id": "01a1d3b9-2c4e-7f10-8a3b-1d2e3f4a5b6c",
      "run_kind": "job",
      "job_key": "daily_orders",
      "location_id": "01a1d38b-e214-7151-8c8e-8606917c3ee6",
      "target": "production",
      "outcome": "partial",
      "failed_nodes": [
        {
          "node_key": "model:fct_orders",
          "error_code": "E100",
          "message": "Conversion Error: Could not convert string 'n/a' to INT32",
          "path": "models/marts/fct_orders.sql"
        }
      ],
      "failed_node_count": 1
    }
  }
}
```

Delivery is at least once and in order. A response other than `2xx`, or no response within 10
seconds, stops delivery and retries the same event. Deduplicate by `event_id`, which the
`Idempotency-Key` header repeats.

| `kind` | Sent when | Fields |
| --- | --- | --- |
| `heartbeat` | Each server replica is alive, periodically | `replica_id`, `store_bytes` (the control database size on disk) |
| `scheduler_no_leader` | No server holds the scheduler lease | None |
| `tick_overdue` | A schedule tick is late | `trigger_id`, `scheduled_for` |
| `calendar_horizon_low` | A running calendar schedule has a day or less of dates left | `trigger_id`, `refresh_at`, `horizon_end` |
| `location_broken` | Every instance of a location and target has stopped reporting for over 90 seconds | `location_id`, `target`, `last_seen_at` |
| `launch_failed` | Starting a worker failed; it may still start | `run_id`, `claim_id`, `code` |
| `run_failed` | A job, group or ad-hoc run ends `failed` or `partial` | `run_id`, `run_kind`, `job_key`, `location_id`, `target`, `outcome`, `failed_nodes`, `failed_node_count` |
| `trigger_skipped` | The scheduler skips a trigger whose stored job or snapshot can't be read, or a sensor whose check failed; the sensor is checked again a minute later | `trigger_id`, `snapshot_id`, `reason` |
| `sensor_rechecked` | A sensor's last check can't be read, so it is checked again from scratch | `trigger_id`, `snapshot_id`, `evaluation_id` |
| `calendar_times_dropped` | A publish drops a calendar schedule's due times | `trigger_id`, `snapshot_id`, `times` |

Each condition is sent once when it starts, not on every 30-second scan. Monitor heartbeats from
outside the server too: a stopped server can't report its own outage.

For a sensor whose check failed, the `reason` of `trigger_skipped` ends with the error's text, with
credentials redacted, cut to 2,000 characters. It is the first error since the sensor's last
completed check in that snapshot: a later attempt that fails differently sends no new event and
doesn't replace it. Everyone who can view the target sees the reason, and it can quote stored
values.

`run_failed` lists at most 20 failed nodes, ordered by node key; `failed_node_count` is the full
number. A `partial` run is included because some of its nodes failed. `job_key` is `null` for
ad-hoc runs. Each `message` is the node's error text with credentials redacted, cut to 2,000
characters, and `null` when the worker reported none. It can quote warehouse data, so treat the
webhook like other run evidence. `run_failed` events appear only in the webhook, not in the
server's platform history.

## Acknowledge attention items

Anyone who can see a target's runs can acknowledge an item on its Overview's attention list. That
hides the item for everyone viewing the target, and records who did it in the audit log:

- A problem run stays acknowledged until someone undoes it.
- An ongoing condition, such as nodes out of date or a late schedule, stays acknowledged until it
  gets worse, or until `attention_snooze` has passed:

```toml
[server]
attention_snooze = "12h"
```

`attention_snooze` takes a duration in days, hours, minutes and seconds, such as `"24h"` (the
default), `"90m"` or `"1d12h"`. `"0"` removes the time limit, so an acknowledged condition stays
hidden until it gets worse or clears. Years and months aren't accepted.

When the Overview finds that an acknowledged condition has cleared, it withdraws the
acknowledgement, so the condition shows again if it comes back. The audit log records that
withdrawal as automatic. Acknowledgements are audit records, so `audit_days` also limits how long
one without a time limit lasts.

The Overview withdraws an acknowledgement of nodes out of date only once the target's warehouse sync
has reported and settled. On a target without sync history, or where you may not read its sync
status, it isn't withdrawn automatically and lapses only after `attention_snooze`.

## Back up the control database

With no `SQLBUILD_CONTROL_DATABASE_URL`, the server keeps its control database in one SQLite file.
Back it up with SQLite's online backup while the server runs:

```bash
sqlite3 control.sqlite3 ".backup '/backups/control.sqlite3'"
```

| Store | Back up with | While the server runs |
| --- | --- | --- |
| SQLite | `sqlite3 <file> ".backup '<copy>'"` or the SQLite backup API | Yes |
| SQLite | A copy of the database file together with its `-wal` file | No; stop the server first |
| PostgreSQL | `pg_dump` | Yes |

- Never copy the SQLite database file alone. Recent commits can still be in the `-wal` file next to
  it, so the copy misses them.
- Restore a backup while the server is stopped, and delete any `-wal` and `-shm` files left beside
  the database you replace.

## Upgrade

Upgrade the server first, then the locations and workers that connect to it. On start, the server
migrates its control database to the schema of its release in one transaction, keeping people,
roles, tokens, triggers and run history. Releases with an older schema refuse the database
afterwards, so back it up before you upgrade (see
[Back up the control database](#back-up-the-control-database)). To roll back, restore that backup;
runs recorded since the upgrade are lost.

A run stays pinned to the snapshot it started on, and a snapshot an earlier release published can
hold job definitions this release no longer reads. Upgrade in this order:

1. Pause every schedule and sensor, and start no manual runs. Keep the scheduler running through
   step 2: it launches queued runs and advances group runs.
2. Let queued and running runs finish, or cancel them.
3. Stop every server process and every separate `sqb scheduler` on the control database before the
   new release starts, or migrates the database with `sqb server migrate` or `sqb admin`.
4. Start the servers and schedulers again on the new release.
5. Upgrade and restart every location, so each publishes its project again with the new release.
6. Once every location has published again, resume schedules and sensors.

Until a location whose snapshot this release can't read has published again, its job pages, group
runs and ad hoc runs fail, and a schedule or sensor that starts a group is skipped and tried again
every minute. A failed job run on such a snapshot isn't retried.

To see what an upgrade changes before you start the server, run the new release with `--dry-run`:

```bash
sqb server migrate --dry-run
```

```text
The control store would migrate from schema version 1 to 2:
  0002_add_skipped_runs
```

`sqb server migrate` without `--dry-run` applies the migrations and exits. It takes the same
`--database-env` and `--config` options as `sqb server`, given before `migrate`.

The server refuses a control database it can't migrate and leaves it unchanged:

| Control database | Fix |
| --- | --- |
| Written by a newer release | Run the release that last opened it, or a later one. |
| Older than the oldest schema this release migrates | Open it once with an earlier release that still migrates it, then with this one. Or start a new, empty store with the command in the message, which discards its history. |
| Same schema version but a different schema, as from a development build | Start a new, empty store with the command in the message. |

Don't downgrade the server after a location or worker has connected from a newer release; the
server can't read what they wrote.

| Newer than the server | What happens | Fix |
| --- | --- | --- |
| Worker | The worker refuses the run and stops with the message below. | Upgrade the server, then rerun the run. |
| Location | The server refuses the location's publication with `API rejected the request with HTTP 400 Bad Request`. The previous snapshot stays current. | Upgrade the server, then restart the location so it publishes again. |

```text
the control server is older than this worker and refused its run report; upgrade the server before its workers
```

A server newer than a worker can send it a run request with a field or a value, such as a new
command, that the worker's release can't read. The worker doesn't run part of what was asked: it
fails the run with a reason naming what it can't read and where, before any warehouse work, and
the run can be rerun once the location is upgraded:

```text
this worker runs SQLBuild 0.256.0 and can't read a run request from a newer server (unknown field `claim.request.<field>`); upgrade the location
```

Some migrations add an index, which the server builds when it migrates. On PostgreSQL that build
locks its table against writes, so on a large table those writes wait until it is built. Migration
`0003` indexes acknowledgements in the audit log, so on a large audit log it holds up audit writes,
including sign-ins. To avoid that, build the index yourself before you upgrade, without blocking
writes:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS sqb_security_audit_attention ON sqb_security_audit((scope_json ->> 'location_id'), (scope_json ->> 'target'), (scope_json ->> 'key'), storage_id) WHERE action IN ('attention.acknowledged', 'attention.acknowledgement_withdrawn');
```

The migration then finds the index already there and skips it.

## Set retention

Set how much history the server keeps in the `[retention]` section of `server.toml`:

```toml
[retention]
statistics_days = 30
audit_days = 730
snapshot_count = 20
run_log_days = 7
run_log_count = 100
state_history_versions = 10
run_output_days = 7
```

| Data | `[retention]` key | Option | Default | Range |
| --- | --- | --- | --- | --- |
| Hourly warehouse statistics | `statistics_days` | `--statistics-retention-days` | `90` | `1`–`65535` |
| Security audit records | `audit_days` | `--audit-retention-days` | `400` | `1`–`65535` |
| Published snapshots per location and target | `snapshot_count` | `--snapshot-retention-count` | `10` | `1`–`65535` |
| Logs of finished runs | `run_log_days` | `--run-log-retention-days` | `14` | `1`–`65535` |
| Finished runs per location and target that keep their logs | `run_log_count` | `--run-log-retention-count` | `200` | `1`–`65535` |
| Builds and check results kept for each node | `state_history_versions` | `--state-history-retention-versions` | `5` on SQLite, `20` on PostgreSQL | `1`–`65535` |
| Output that finished runs printed | `run_output_days` | None | `run_log_days` | `1`–`65535` |
| Skipped and covered schedule ticks | None | None | 30 days | Fixed |

Statistics samples older than the horizon disappear from statistics reads at once and are then
deleted in the background.

A security audit record older than the horizon is deleted only when it is no longer needed:

- The webhook in `SQLBUILD_SECURITY_AUDIT_WEBHOOK_URL`, if set, has received it.
- No retained run's retry depends on it. A manual job or rerun request keeps its record while
  the run exists.
- It is not the newest record, so audit page cursors never see a reused position.

Records kept past the horizon for these reasons are reported on stderr as
`Security audit retention: retained past horizon: N` whenever the count changes. A growing count
usually means the audit webhook is failing.

The server keeps the newest published snapshots for each location and target. It deletes an older
snapshot only when no retained run, job, trigger, trigger change or location request uses it, and
deletes its node definitions and SQL text when no other snapshot shares them. Repeating or
interrupting this cleanup is safe.

A finished run loses its log, the events, statements, SQL and output its worker recorded, when it
is older than `run_log_days` or when more than `run_log_count` newer runs
have finished in its location and target, whichever comes first. The run itself, its node results,
and the run history the scheduler recorded stay, so run lists, node status and history are
unchanged; only the run's log, statements and SQL are no longer shown. A running run keeps its log.

Locations copy the builds and check results recorded in the warehouse's
`_sqlbuild_fingerprints` and `_sqlbuild_audit_results` tables into the control database. The
server keeps the newest `state_history_versions` builds of each node and results of each check,
and always keeps the latest one:

- A location's first read of a table, and its periodic full re-read, take only the newest
  `state_history_versions` rows of each node or check from the warehouse.
- Builds and results that arrive later are added, and older ones are deleted in small batches about
  once a minute.
- A SQLite control database gives the freed space back to the disk a little at a time, so the file
  shrinks.

The PostgreSQL default matches the janitor's
[`direct_state_history_versions`](/docs/cli/janitor#state-history-pruning), so with the janitor
running the server keeps what the warehouse keeps. [`sqb dev`](/docs/cli/dev/) has no
`server.toml` and uses the SQLite default.

The **Server** panel on the **Settings** page shows the control database's size on disk and both
run log limits, and each `heartbeat` [platform event](#receive-platform-events) carries the size as
`store_bytes`.

The scheduler deletes covered and skipped ticks older than 30 days. It keeps each trigger's latest tick and
every tick that started a run. A new schedule, a resumed trigger or a cursor reset catches up only
on the latest missed time, so deleted ticks never come back.

An invalid value stops the server before it opens the control database. Servers that share one
control database delete at the shortest horizon among them and count only their own audit
webhook, so give them the same values and webhook.

## Keep run output

Everything a run prints goes to the server's output store, filed under the node that printed it.
Output printed outside any node, such as the worker's own messages, is filed under `run`. The
store keeps each node's stdout and stderr in zstd-compressed files of a few MB. The control
database keeps only a small index: where each node's lines are, and which lines look like errors
or warnings. A run that prints gigabytes does not grow the control database.

Set the store in the `[output]` section of `server.toml`:

```toml
[output]
store = "file:///var/lib/sqlbuild/output"
max_bytes_per_run = "20GB"
```

- `store` is a local folder, `file:///path`, or an S3 prefix, `s3://bucket/prefix`. By default it
  is an `output` folder beside a SQLite control database. With PostgreSQL it is
  `~/.local/state/sqlbuild/output` of the user that runs the server, or `sqlbuild/output` in
  `XDG_STATE_HOME` when that is an absolute path, whichever directory the server starts in. In the
  server image that is `/home/sqlbuild/.local/state/sqlbuild/output`.
  [`sqb dev`](/docs/cli/dev/) keeps its output in `.sqlbuild/output` with its default control store.
  With `--control-store-url` it uses an `output` folder beside that SQLite store, or the same folder
  as above for PostgreSQL.
- `~` is `HOME` (`USERPROFILE` on Windows), or the account's home directory when that is unset.
- Servers on different control databases under the same user, including a server on a cloned
  database, should each set their own `store` folder, or one's retention can delete another's
  output.
- A local folder must be on a persistent volume, not inside the server's container, or recreating
  the container loses every run's output. `compose.yml` and the Podman Quadlet example mount a named
  volume at `/home/sqlbuild/.local/state/sqlbuild/output`. If you set another folder, mount a
  volume there that user 10001 can write to.
- Use an S3 prefix when several servers share one control database, or when a replacement server
  can't mount the same volume. The server reads AWS credentials from the standard AWS environment
  variables or from the role it runs under.
- `max_bytes_per_run` is a number of bytes or text such as `"500MB"` or `"2GiB"`. Past it a run
  keeps its first half and its newest half, and the lines in between are counted where they were
  left out. By default a run keeps all of its output.

If the service user's home can't be written, as with systemd's `DynamicUser=`, give the server a
state folder in its unit. Output then goes to `/var/lib/sqlbuild/sqlbuild/output`:

```ini
[Service]
StateDirectory=sqlbuild
Environment=XDG_STATE_HOME=/var/lib/sqlbuild
```

The server prints `Run output store: ...` when it starts, with a local folder as an absolute path.

Reading a run's output needs `view.evidence` on every node the run selected. The security audit
records each search and download. The run page reads a run's lines and index every few seconds while
it follows the run, so each server records those reads once in 10 minutes for each person, run and
kind of read. People read a node's output with its stdout and stderr lines in the
order printed, or one stream of it, or the whole run's output with each line's node. They page
forwards and backwards, read the last lines, fold runs of similar lines, search in either direction,
jump to error and warning lines, or download a node's output whole. No read loads a whole log at
once.

A worker sends what it prints in batches of about 4 MB, or every 2 seconds. When a node prints
faster than the worker can send, the node waits for the worker. If the server stops accepting
output for 30 seconds, the worker drops what it cannot send. It prints
`Run output: N bytes of run output were not stored` to its log, with the reason, and adds the same
warning to the run.

A finished run's output is deleted `run_output_days` after the run ended; the run, its node results
and the lines its nodes logged with `ctx.log` stay.

Upgrade the server before its workers. An older server keeps none of a newer worker's output, and
the worker's log says `the control server is older than this worker and does not accept run output;
upgrade the server before its workers`. A node that logs with `ctx.log` fails on an older server
with the same request to upgrade it.

## Grant roles to OIDC groups (beta)

With OIDC sign-in, members of an identity-provider group can get a role without a per-person
assignment. Add `groups_claim` and `group_roles` to the `[oidc]` section of `server.toml`:

```toml
[oidc]
origin = "https://control.example.com"
issuer = "https://login.example.com"
client_id = "orders-control"
groups_claim = "groups"

[oidc.identities]
orders-person = "0190c3c1-5a4e-7b8e-9f00-2a7d1c9e4b11"

[[oidc.group_roles]]
group = "orders-operators"
role = "operator"
location_id = "0190c3c1-6b2f-7c3d-8e44-5f1a2b3c4d5e"

[[oidc.group_roles]]
group = "orders-readers"
role = "viewer"
```

| Key | Meaning |
| --- | --- |
| `groups_claim` | ID-token claim that lists the person's groups. Required when `group_roles` is set. |
| `group_roles[].group` | Group name exactly as the claim lists it. |
| `group_roles[].role` | `viewer`, `operator`, `developer` or a project role the location publishes. Not `admin`. |
| `group_roles[].location_id` | Limits the role to one location. Required for a project role or a target. |
| `group_roles[].target` | Limits the role to one target in that location. |

Groups grant roles only to people who already have an entry in `identities`; a group never
creates an account. Group roles add to the person's own role assignments.

The server reads groups only from the signed ID token, at sign-in. Each sign-in replaces the
person's groups with the ones in that token:

- Removing someone from a group in the identity provider stops the grant at their next sign-in.
  Until then, all of their sessions use the groups from their most recent sign-in.
- Removing or changing a `group_roles` entry and restarting the server changes access at once,
  without a new sign-in.
- A claim that is missing, is not a list of non-empty names, or is replaced by an overage pointer
  gives no groups.

The server refuses to start when a mapping grants `admin`, scopes a project role or target without
a location, has a blank group, or when `group_roles` is set without `groups_claim`.

Servers that share one control database must use identical OIDC and `group_roles` configuration.
Different configurations on one database are unsupported: the last server to start decides the
group mapping for all of them.

## Inspect published SQL

Sign in with [`sqb login`](/docs/cli/login/), then inspect one exact node in the current
successful publication:

```bash
sqb control sql model:orders \
  --server https://control.example.com \
  --location-id "$LOCATION_ID" \
  --target development
```

The command uses your saved person session and prints JSON. It does not load a local project
or open a warehouse connection. Use `--ca-cert PATH` for an additional trusted PEM certificate.
The node key is exact: `model:orders+` does not expand a selector. Progress and failures go to
stderr; a failed request prints no SQL to stdout. Permission denials include their decision ID.

The equivalent person-authenticated API is a `GET` request to
`/api/control/locations/{location_id}/targets/{target}/nodes/{node_key}/sql`.

Developer or Admin access must cover the requested location and target, or a
[project role](#define-project-roles) must grant `view.sql` on the node. Viewer, Operator and
the configurable default Viewer role do not grant SQL inspection. The response contains the
snapshot ID, exact node key, raw SQL and compiled SQL. Missing SQL fields are `null`; an absent
current publication or node returns JSON `null` after authorization.

SQL inspection does not execute SQL or return Python source, execution artifacts, logs or sample
data. Every successful inspection records an audit entry without copying SQL into it. If the
audit cannot be saved, the request fails without returning SQL. Revocation takes effect on the
next request, including sessions created by [`sqb login`](/docs/cli/login/).

## Sync from the warehouse now

A code location reads what has been built, checks and freshness back from the warehouse when it
starts, after each run the server starts has ended, and at least every 30 minutes. To pick up a
`sqb build` you run on your own machine straight away, name the server and location in
`sqlbuild_project.toml` and sign in with [`sqb login`](/docs/cli/login/):

```toml
[control]
server = "https://control.example.com"
location = "orders-warehouse"
```

Each `sqb build` then asks that location to sync the target the build used, and prints one line
saying whether it did. You can also select **Sync now** on the location's page, or run:

```bash
sqb control sync \
  --server https://control.example.com \
  --location-id "$LOCATION_ID" \
  --target development
```

The command prints `{"applied": true}` when the server has queued the request, and
`{"applied": false}` when a sync for that target is already waiting, which covers this request too.
The location starts the sync within a few seconds, and the top bar shows when it last synced.

| Setting | Environment variable | Default | Meaning |
| --- | --- | --- | --- |
| `[control] server` | `SQLBUILD_CONTROL_SERVER` | none | HTTPS origin of the server, as `sqb login --server` takes it |
| `[control] location` | `SQLBUILD_CONTROL_LOCATION` | none | Location name a signed-in `sqb build` asks to sync |
| `[control] sync_at_least_every` | `SQLBUILD_CONTROL_SYNC_AT_LEAST_EVERY` | `"30m"` | Longest a location waits between syncs; `"0"` or `"off"` turns it off. Databricks, ClickHouse and MotherDuck never sync on the interval. See [warehouse cost](#warehouse-cost-of-an-always-on-location) |
| none | `SQLBUILD_CONTROL_CA_CERT` | none | Extra trusted PEM CA certificate for the server |

An environment variable overrides the project file. `sqb location serve --sync-at-least-every`
overrides both. The interval uses the project's duration syntax, such as `"45m"` or `"2h"`, and
must be at least `"1m"`.

Requesting a sync needs the same access as a connection test: Developer or Admin on the location
and target. Viewer and Operator cannot request one. Every request is recorded in the audit log.

Details:

- The sync after a build never changes the build's exit code and gives up after 5 seconds. It
  prints nothing when `[control]` sets neither key or nobody is signed in to that server. When the
  location is not one you can view, it prints `Warehouse sync skipped:` and the reason.
- Requests that arrive while a sync is running, from builds, **Sync now**, ended runs or the
  interval, add one more sync after it, not one each.
- The interval restarts after every completed sync, so a location that syncs often for other
  reasons never syncs extra.
- A sync reads the warehouse and writes only to the dynamic pause table: on Snowflake, after it
  completes, it resumes the [dynamic models](/docs/concepts/models/dynamic#when-a-build-dies) whose
  pausing build has been silent past `[dynamic] heartbeat_grace`, and records that in the pause
  table as `location-sync:<location ID>`. Before resuming, it records a `resuming` claim on each
  model and reads the holds again, so a build that paused the model meanwhile keeps it paused; a
  build that finds an open claim waits for it to close. A claim older than 2 minutes, the time a
  sync gets to resume, is treated as abandoned. It checks the pause table in the target's schema and in every
  schema the location's models write to. A model that fails to resume is logged as
  `Resuming an expired dynamic hold failed: <model>: <error>`, keeps its hold, and is retried on
  the next sync; the others still resume. Other adapters can't build dynamic models, so their
  syncs don't open a session for this.
- On Snowflake, a sync skips state tables that haven't changed since the last sync, the pause
  table included, so a sync with nothing new doesn't resume the warehouse.
- When a read fails, the Connections page shows the warehouse error. A read that ran out of memory
  or time retries a smaller page. Any other error, such as a missing permission or table, retries
  after 30 seconds, then waits twice as long after each failure in a row. After 5 failures in a row
  the sync stops until a run ends, you request one, the location publishes again, or the next safety
  sync is due (`sync_at_least_every`). It then starts again from the first kind of history, and
  failed reads back off again before they stop it.
- `[control]` holds no secrets. The session stays in the login `sqb login` saved for that server.
- When a state table holds two rows with the same ID, such as one check result written twice, the
  server keeps the row with the earlier time. Estimated query costs are the exception: when two
  builds refresh the same estimate at once, they can write the same ID, and the server keeps the
  later row, the one the warehouse treats as current. A server that kept a different row corrects it
  at the location's next full reread, which runs when the location starts and on the first sync at
  least 5 minutes after the previous full reread.

### Warehouse cost of an always-on location

A location syncs when it starts, after each run ends, when someone asks, and on the
`sync_at_least_every` interval. Which reads need running compute depends on the adapter:

| Adapter | Reads that need running compute | Interval sync while idle |
| --- | --- | --- |
| Snowflake | Reading a state table that changed since the last sync. Change checks, the catalog (`SHOW TABLES`, `SHOW VIEWS`, `SHOW COLUMNS`), statistics (one `SHOW OBJECTS` per schema) and existence checks run in cloud services | Every 30 minutes. A sync with nothing new resumes no warehouse; one after another writer changed a state table resumes it once |
| BigQuery | None to resume, but every sync queries each state table and is billed for the bytes it reads | Every 30 minutes |
| Databricks | Every read, including the catalog and existence checks, runs on the SQL warehouse | Off: a stopped warehouse would start each time |
| ClickHouse | Every read is a query, which wakes an idle ClickHouse Cloud service | Off |
| MotherDuck | Every read runs on MotherDuck compute | Off |
| PostgreSQL, SQL Server | The server is always running; a serverless database that pauses when idle wakes on connection | Every 30 minutes; set `sync_at_least_every = "off"` for one that pauses |
| DuckDB, SQLite | None; the location reads the file | Every 30 minutes |

Where the interval is off, an idle location syncs only after a run ends or when someone asks, with
**Sync now**, `sqb control sync` or a signed-in `sqb build`. A run has just used the warehouse, so
the sync after it rarely resumes anything. Setting `sync_at_least_every` doesn't change this.

### Follow a sync

The location prints a line as it finishes each of its 14 kinds of history, then a summary:

```text
Reading warehouse history for automatic synchronization...
Warehouse history 1/14: fingerprints, 1,204 rows in 0.8 s
Warehouse history 2/14: source freshness, unchanged in 0.1 s
...
Warehouse history synchronization completed: 14 kinds, 31,204 rows in 12.8 s.
```

A page holds up to 2,000 rows and ends early at 8 MiB, so wide rows make smaller pages. A failed
read prints which kind failed, the page size and why, then what the location does next. A read that
ran out of time or memory retries a smaller page; any other failure retries the same page after a
wait that doubles each time, and the fifth in a row stops the sync:

```text
Warehouse history read failed for statistics (100-relation page): no reply within 130 s. Sync incomplete; retaining mirror and retrying a smaller page in 30 s.
Warehouse history read failed for catalog (2000-row page): permission denied for table _sqlbuild_catalog. Sync incomplete; retaining mirror and retrying in 60 s.
Warehouse history read failed for catalog (2000-row page): permission denied for table _sqlbuild_catalog. Synchronization stopped after 5 failed reads in a row; it resumes after the next run, on request or after a publish.
```

| Cause | Printed as |
| --- | --- |
| The location couldn't start its reader | `the metadata reader did not start:` and the error |
| The warehouse refused the connection or the query | The warehouse's message |
| No reply in time | `no reply within N s`: 120 s for a page, or 30 s plus 1 s per relation for a statistics page |

The location's page shows a running sync, for example
`syncing history 9/14 · catalog · 1,640 rows`, and the last full sync's kinds, rows and time.

A location is ready as soon as it has compiled and published; nothing waits for the sync. Lineage,
jobs, the catalog and code work at once. Plan previews, node history, check results and costs read
the server's copy of the warehouse, so until the location's first sync completes they show
**Syncing warehouse history** with its progress, and fill in when it does.

The location's page shows a failing sync as **failing** with when it last synced; its tooltip lists
each failing kind with the cause, the page size and the warehouse's message, shortened and with
secrets removed. The Connections page shows a stopped sync as **stopped after failed reads**.

## Skip overlapping runs and retry failures

Declare who owns a job, whether scheduled requests wait for a running copy, and how often a failed
run retries:

```toml
# orchestration/jobs/nightly_orders_job.toml
name = "nightly_orders_job"
description = "Orders and their daily totals"
select = "+order_totals"
owner = "Orders team"
overlap = "skip"
schedule = { cron = "0 2 * * *", timezone = "UTC" }

[retry]
attempts = 3
delay_seconds = 600
```

| Setting | Values | Default | Effect |
| --- | --- | --- | --- |
| `owner` | Any non-blank text | None | Shown on the job's page and in the job list |
| `overlap` | `queue` or `skip` | `queue` | With `skip`, a schedule tick or sensor request that arrives while a run of the job is queued or running starts no run |
| `retry` | `attempts` from 2 to 11, `delay_seconds` from 0 to 86400 | None | A failed or partial run nobody cancelled reruns its failed, cancelled and skipped nodes, and those it never reached, after the delay, until it succeeds or has run `attempts` times in all |

A skipped tick shows as **skipped** in the trigger's tick log, with the run it yielded to, and
creates no run. A sensor tick lists the requests it skipped the same way.

| Sensor watches | A request skipped while the job runs |
| --- | --- |
| Run, node or platform events | Is dropped |
| New source data or stale sources | Is checked again on the next check and starts a run once the job is idle, if the source is still new or stale |
| Custom code | Starts a run once the job is idle if the code returns the same run key again |

Details:

- Runs people start, reruns and backfills always queue, whatever the job's `overlap`.
- A tick that makes up for several missed times, after the scheduler was down or the trigger was
  paused, still queues.
- A retry waits in the queue until its delay ends, and the run list shows it as a rerun of the run
  that failed. Cancelling a run stops its retries.
- A member job's `[retry]` also applies inside a group run. When the member fails, the group runs it
  again after `delay_seconds`, inside the same group run, and the jobs that depend on it wait
  instead of skipping. The group keeps its pool slots meanwhile.
- A group's own `[retry]` is a final sweep: after the group run ends `failed` or `partial`, it
  queues one new linked rerun of the group's failed, cancelled and skipped nodes, and those it never reached.
- So a retry of a whole run, a job's or a group's, is a new linked run, and a retry of a member
  stays inside its group run.
- Sensors and alerts see a member's final attempt only. The group run's timeline shows each retry,
  such as `orders_job failed, retrying in 15 min (attempt 2 of 3)`, the member's row shows its
  attempt, and the run's header counts the members it retried.
- An invalid value is a `D017` error at its line, such as
  ``orchestration/jobs/nightly_orders_job.toml:6:11: unknown variant `coalesce`, expected `queue` or `skip` ``.

## Limit worker containers

A Docker worker starts with its location container's memory, CPU and process limits. Set limits
for every run of a launcher in its `run` table, and for one job with `resources`:

```toml
[[launchers.docker]]
location = "orders"
target = "development"
server_url = "http://server:8000"
max_workers = 2
socket = "/var/run/docker.sock"
location_container = "orders-location"
executable = "/usr/local/bin/sqb"

[launchers.docker.run]
memory = "1g"
cpus = 1
pids = 512
max_memory = "4g"
```

```toml
# orchestration/jobs/nightly_orders_job.toml
name = "nightly_orders_job"
description = "Orders and their daily totals"
select = "+order_totals"

[resources]
memory = "3g"
cpus = 2
```

| Setting | `run` table | `resources` | Value |
| --- | --- | --- | --- |
| `memory` | Yes | Yes | Bytes, or a size such as `"512m"` or `"2g"` |
| `cpus` | Yes | Yes | A positive number, such as `0.5` |
| `pids` | Yes | Yes | The most processes, a positive whole number |
| `cgroup_parent` | Yes | No | The cgroup workers start under |
| `max_memory` | Yes | No | The most memory any worker of the launcher gets |

- A job's `resources` win over the launcher's `run` table, which wins over the location
  container's limits.
- A worker never gets more than `max_memory`: a job that asks for more gets `max_memory`.
  Without `max_memory`, a job's `resources` can't go above the location container's memory, CPU
  or process limits; set `max_memory` to let jobs ask for more memory than the location has.
- Workers keep the location container's dropped capabilities and security options, such as
  `no-new-privileges`.
- A job in a group uses its own `resources`. Local launchers ignore `resources`.
- An invalid value fails publication with the job's name, such as
  `job nightly_orders_job resources: cpus must be a positive number`.

## Cap pools

A project declares each [pool](/docs/concepts/concurrency#jobs-sharing-something-else-pools)'s
limit. To keep one launcher's runs below it, lower the limit with `pool_caps`:

```toml
[[launchers.local]]
location = "orders"
target = "production"
server_url = "http://127.0.0.1:8000"
max_workers = 4
project_dir = "/srv/orders"
executable = "/usr/local/bin/sqb"

[launchers.local.pool_caps]
warehouse_heavy = 1
```

- A cap lowers a limit and never raises it. A pool without a cap keeps the project's limit.
- A job taking more slots than the cap takes the whole capped pool.
- A cap applies to its launcher's location and target only.
- A cap for a pool the project doesn't declare has no effect.

`max_workers`, write claims, `overlap` and pools are compared on
[Concurrency](/docs/concepts/concurrency).

A job's run builds `--select job:<name>`, as `sqb build --select job:<name>` would on the command
line, so the job's `concurrency`, `full_refresh`, `run_tests` and `ignore_audit_failures` apply to
its nodes the same way. A group runs each of its jobs as its own run.

## Run ad-hoc commands

People with `run.adhoc` can run a `sqb` command on the current publication without declaring a
job. Use the web UI's plan page, or send the command as argument tokens after `sqb`:

```json
{
  "location_id": "0191f0aa-0000-7000-8000-000000000001",
  "target": "development",
  "command": ["build", "--select", "+orders", "--full-refresh"],
  "priority": 0
}
```

`POST /api/control/runs/adhoc/check` with this body is a dry run. It returns the exact nodes the
command selects (`selection`), the nodes it writes (`write_set`), the options the worker receives
(`settings`), and each permission it needs with your decision (`permissions`). `error` explains a
command that can't run whatever your permissions, and `launchable` is `true` when the launch
would be accepted. A dry run queues nothing and records no audit entry.

To launch, `POST /api/control/runs/adhoc` with the same fields plus a `reason` and a new `run_id`,
a random (version 4) or time-ordered (version 7) UUID. The response is `{"applied": true}`;
sending the same `run_id` again returns `{"applied": false}` and starts nothing. Job runs and
reruns take a `run_id` the same way. The server refuses a name-based (version 5) `run_id` with a
400, because it derives those IDs for the runs it starts itself. The server resolves selectors
against the current publication, and the worker runs exactly the resolved nodes, from the project
it verified against that publication; files that change on the location after that check are not
used. The target is always the one in the request.

| Verb | What the worker runs |
| --- | --- |
| `build` | The selected nodes, with their tests and audits |
| `test` | The SQL tests of the selected models |
| `audit` | The audits of the selected nodes, against what is already built |
| `seed` | The selected seeds; other selected nodes are left out |
| `freshness` | The selected sources and every source upstream of the selection |
| `load` | The loaders of the selected managed sources, as a build of those sources without tests or audits |
| Any other verb | Refused |

Only `build`, `seed` and `load` write, so `test`, `audit` and `freshness` runs never wait for other
runs. A `build` loads the managed sources its models read, as `sqb build` does, under `run.adhoc`
alone; `--no-load` turns that off.
A `test` or `audit` run reports each selected node with the worst result of its tests or audits.

Selectors use the CLI grammar: names, `seed:`, `source:`, `tag:`, `path:`, `test:` and `job:`,
with `+` for upstream or downstream nodes. Positional selectors work as on the command line.

A `build` whose selection names a job takes the job's settings, exactly as `sqb build` and the
job's own runs do; see
[Settings when a build names a job](/docs/concepts/orchestration#settings-when-a-build-names-a-job).
The server freezes each named job with the run: the nodes that take its settings and the settings
themselves, as published. A rerun keeps those jobs, narrowed to the nodes it reruns, and works out
what it writes from the same settings. Ad-hoc runs never retry, so a job's `[retry]` doesn't
apply to them.

Applying a job's settings needs the permissions running that job needs: `job.run` for each named
job that gives the build a setting the command line doesn't replace, and `run.rewrite_history` or `run.load` when the job's own
settings rewrite history (`full_refresh`, a cursor or an `allow_*` setting) or load sources
(`reload`, `load_sources`), on top of what the typed flags need. With `job.run`, a job's settings
that are refused when typed, such as `defer_to` or `plan_from`, apply as they do in the job's own
runs. The job's `vars` and `warehouse` need no `run.vars` or `run.warehouse`, which gate only what a
person types. A warehouse every named job shares is the whole build's, so it counts as applied
whatever the adapter. A named job that gives the build nothing, because it has no settings, the
command line replaces them, or it keeps none of the selected nodes and sets nothing build-wide,
needs only `run.adhoc`.

Upgrade the server and every location, and let each location publish again, before running ad-hoc
commands that name a job. A location that hasn't been upgraded runs such a command without the
job's settings, and refuses a plan of it.

| Flags | Verbs | Needs |
| --- | --- | --- |
| `--select`, `-s`, `--exclude` | All | `run.adhoc` on every selected node |
| `--full-refresh`, `--start-cursor`, `--end-cursor`, `--start-cursor-ts`, `--end-cursor-ts`, `--start-cursor-int`, `--end-cursor-int` | `build` | `run.rewrite_history` |
| `--allow-snapshot-full-refresh`, `--allow-snapshot-schema-change`, `--allow-table-type-downgrade`, `--allow-retention-decrease` | `build` | `run.rewrite_history` |
| `--warehouse` | All | `run.warehouse`, and the warehouse configured for the target on the location |
| `--vars` | All | `run.vars`, also to preview a plan with them |
| `--load`, `--reload`, and the `load` verb | `build`, `load` | `run.load` on the sources the run loads |
| `--max-microbatches`, `--no-load`, `--no-tests`, `--no-audits`, `--no-python`, `--fail-fast`, `--selection-diagnostics`, `--verbose` | `build` | `run.adhoc` |
| `--concurrency` | `build`, `test`, `seed`, `audit` | `run.adhoc` |
| `--test-timeout` | `build`, `test` | `run.adhoc` |
| `--case`, `--inspect` | `test` | `run.adhoc` |
| `--state`, `--fail-on-error`, `--fail-on-stale` | `freshness` | `run.adhoc` |

A priority above 0 also needs `run.prioritise`. Among built-in roles only Admin grants
`run.rewrite_history`, `run.warehouse`, `run.vars`, `run.load` and `run.prioritise`. Every other
flag is refused with its reason:

| Refused flags | Reason |
| --- | --- |
| `--defer-to`, `--defer-sources-to`, `--defer-clone-from` | They read another target |
| `--allow-missing-migration-origin` | It can lose data |
| `--no-sql-analysis`, `--no-cache` | Workers verify the published SQL and manage their own cache |
| `--debug` | It prints executed SQL |
| `--since`, `--explain` | They need the worker's Git checkout |
| `--select-file` | It reads a file on the worker |
| `--target`, `--project-dir` and the `--dbt-*` paths | Workers run the published project for the request's target |
| `--json`, `--json-output`, `--event-output`, `--manifest`, `--no-color` | Workers own the run's output |

For an ad-hoc run, the worker checks `--warehouse` against the warehouses the location
configures for the target before any statement runs. An unconfigured warehouse fails the run with
the reason `the requested warehouse is not configured for this target on this location; no
warehouse statement ran`, which the run page shows. A named job's own `warehouse` setting is not
checked this way.

A run with `--vars` is checked against the publication like any other run. The worker then
compiles the project again with the variables and records the compiled hash of each of the run's
nodes on the run before any statement runs.

## Plan builds

Anyone with `view` on every node of a target can see what a `build` command would do before it
runs. The web UI's plan page does this for every Run button: the location serving the target runs
[`sqb plan --json`](/docs/cli/plan/) on the command's nodes, and the page shows each model's action
and reason, backfills, migrations and warnings. Running the command still needs `run.adhoc`.

A plan of a command that names a job takes the job's settings as the run would, from the jobs the
server froze with the request, so the plan shows the job's full refreshes, concurrency and, for a
job that sets `changed`, what changed. It fails as the run would when the job's warehouse can't be
selected. A plan never takes a warehouse a person types, but a typed `--warehouse` still replaces
the job's own, as it does in the run.

A plan reads the server's synced copy of the target's warehouse metadata, not the warehouse, so
planning never resumes a suspended warehouse. The page shows when that copy synced, or that it
hasn't fully synced yet. Each incremental model's range starts where its last successful build
ended and runs to the latest data when the run starts. The run plans again against the warehouse.
These stay unknown until it does:

- source freshness, retention, table types and column rename support;
- sources outside the schemas the server syncs;
- the cursor position of an incremental model with no successful build;
- the range start of an incremental model with lookback, a replay on change, a start override,
  microbatches or a `cursor_start` past its last build;
- whether a start set with `cursor_start_max_ahead` sits too far ahead;
- the columns of an expression source whose SQL changed since it was last described, which the
  plan takes as declared.

A location keeps its last 16 plans for the current publication and synced copy, in memory, and
answers an identical request with the plan it kept instead of planning again, for up to 10
minutes: a plan's incremental windows and expiry follow the time it was made. A newer publication
or synced copy drops them all. A kept plan's `timings` say so in `reused_from`, the time it was
made, and the page shows its age. The page's **Plan again** asks for a fresh plan.

Over the API, queue a plan, then read it until `result_json` is set. `fresh` is required: `true`
plans again even when the location kept a plan for the same command.

```json
POST /api/control/locations/{location_id}/targets/{target}/plans
{ "request_id": "0191f0aa-0000-7000-8000-0000000000a1", "command": ["build", "--select", "+orders"], "fresh": false }

GET /api/control/locations/{location_id}/targets/{target}/plans/{request_id}
```

`result_json.outcome.kind` is `plan`, with the `sqb plan --json` document in `document`, or
`superseded` when the location's project files changed while it planned; plan again. A plan never
appears in Runs and never connects to the warehouse. In `document`, `synced_copy` holds
`synced_at` (`null` until the copy has fully synced), `cursor_window_starts` and
`unknown_until_run`.

| Limit | Value |
| --- | --- |
| Verbs | `build` only |
| Flags | Those accepted for an [ad-hoc run](#run-ad-hoc-commands); `--warehouse` and flags `sqb plan` doesn't take, such as `--fail-fast`, don't change the plan |
| Location | A `sqb location serve` for the target that reported in the last 90 seconds |
| Plans waiting | One per person and four per target |
| Expiry | 10 minutes |
| Plan size | 8 MiB |

Only the person who asked can read a plan. Python source and dependency diffs are left out unless
they also have `view.sql` on every node, and secrets in warehouse error text are redacted.

## Define project roles

Put project roles in `roles.toml` at the project root. `sqb location publish` resolves each
grant's node selectors against the published project:

```toml
[roles.orders_support]
description = "Answer order questions"

[[roles.orders_support.grants]]
nodes = ["tag:orders"]
permissions = ["view.sql", "run.adhoc"]

[[roles.orders_support.grants]]
nodes = ["tag:orders,tag:pii"]
permissions = ["view.evidence"]
```

| Rule | Behaviour |
| --- | --- |
| Selectors | Same grammar as a job's `select`; an unknown tag or name fails publication |
| No matching nodes | Publication succeeds with a warning; the grant gives nothing |
| Permissions | Any non-administrative action; `user.manage`, `role.assign` and `audit.view` are rejected |
| Runs | `job.run`, `run.rerun` and `run.rewrite_history` need the permission on every node the run writes; an [ad-hoc command](#run-ad-hoc-commands) needs `run.adhoc` and its flags' permissions on every node it selects; a priority above 0 also needs `run.prioritise` |
| Republish a location | `location.republish` on the location and target; reading its discovered sets back needs `view` |
| Triggers | `trigger.toggle` (on, off) and `sensor.reset_cursor` (start over, skip an event) need the permission on every node a schedule's job writes. A sensor needs it on every node of the target, as does pausing or resuming a schedule whose job can't be read |
| Listings | The catalog, statistics, providers and run list need `view` on every node of the current publication; partial coverage is denied, not filtered |
| Several roles | Grants add up across a person's roles |

Assign a project role with `POST /api/admin/roles`, using the role key as `role`. Each
publication replaces the location's project roles: new and changed grants apply at once, and
removed roles stop applying. A selector covers newly matching nodes as soon as they are
published. Each change appears in the publication's change list as `role:<key>`. A denial names
only the missing permission, such as `missing view permission for this target`, and its decision
ID. It names no nodes, and an unknown location, job, trigger or run is refused with the same
response. The security audit event for that decision ID lists the nodes the request was missing.
