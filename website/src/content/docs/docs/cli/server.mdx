Run the control API and scheduler without loading project Python:

```bash
sqb server
```

Use `sqb server --help` for service, authentication and launcher options.

## Serve over HTTPS

Code locations and workers send their bearer token with every request to the `--server` URL.
`sqb server` serves plain HTTP, so put TLS or an HTTPS reverse proxy in front of it and give
locations and workers its `https://` URL. When a location or worker connects to an `http://` URL
on another host, it prints this warning once and keeps running:

```text
warning: the bearer token for http://control.example.com travels unencrypted over HTTP; put TLS or an HTTPS reverse proxy in front of the server
```

Connections to `localhost`, `127.0.0.1` or `::1` print no warning.

## Receive platform events

Set `SQLBUILD_PLATFORM_WEBHOOK_URL` in the server's environment to have it `POST` each platform
event to that URL as JSON. Leave it unset to turn delivery off. Locations and workers never
receive the URL.

```json
{
  "storage_id": 4182,
  "event_id": "01a1d3c2-6f0e-7a51-9b2e-3c4d5e6f7a80",
  "occurred_at": "2026-11-13T07:12:04.381Z",
  "payload": {
    "platform": {
      "kind": "run_failed",
      "run_id": "01a1d3b9-2c4e-7f10-8a3b-1d2e3f4a5b6c",
      "run_kind": "job",
      "job_key": "daily_orders",
      "location_id": "01a1d38b-e214-7151-8c8e-8606917c3ee6",
      "target": "production",
      "outcome": "partial",
      "failed_nodes": [
        {
          "node_key": "model:fct_orders",
          "error_code": "E100",
          "message": "Conversion Error: Could not convert string 'n/a' to INT32",
          "path": "models/marts/fct_orders.sql"
        }
      ],
      "failed_node_count": 1
    }
  }
}
```

Delivery is at least once and in order. A response other than `2xx`, or no response within 10
seconds, stops delivery and retries the same event. Deduplicate by `event_id`, which the
`Idempotency-Key` header repeats.

| `kind` | Sent when | Fields |
| --- | --- | --- |
| `heartbeat` | Each server replica is alive, periodically | `replica_id` |
| `scheduler_no_leader` | No server holds the scheduler lease | None |
| `tick_overdue` | A schedule tick is late | `trigger_id`, `scheduled_for` |
| `calendar_horizon_low` | A running calendar schedule has a day or less of dates left | `trigger_id`, `refresh_at`, `horizon_end` |
| `location_broken` | Every instance of a location and target has stopped reporting for over 90 seconds | `location_id`, `target`, `last_seen_at` |
| `launch_failed` | Starting a worker failed; it may still start | `run_id`, `claim_id`, `code` |
| `run_failed` | A job, group or ad-hoc run ends `failed` or `partial` | `run_id`, `run_kind`, `job_key`, `location_id`, `target`, `outcome`, `failed_nodes`, `failed_node_count` |

Each condition is sent once when it starts, not on every 30-second scan. Monitor heartbeats from
outside the server too: a stopped server can't report its own outage.

`run_failed` lists at most 20 failed nodes, ordered by node key; `failed_node_count` is the full
number. A `partial` run is included because some of its nodes failed. `job_key` is `null` for
ad-hoc runs. Each `message` is the node's error text with credentials redacted, cut to 2,000
characters, and `null` when the worker reported none. It can quote warehouse data, so treat the
webhook like other run evidence. `run_failed` events appear only in the webhook, not in the
server's platform history.

## Upgrade

Upgrade the server first, then the locations and workers that connect to it. Don't downgrade the
server after a location or worker has connected from a newer release; the server can't read what
they wrote.

| Newer than the server | What happens | Fix |
| --- | --- | --- |
| Worker | The worker refuses the run and stops with the message below. | Upgrade the server, then rerun the run. |
| Location | The server refuses the location's publication with `API rejected the request with HTTP 400 Bad Request`. The previous snapshot stays current. | Upgrade the server, then restart the location so it publishes again. |

```text
the control server is older than this worker and refused its run report; upgrade the server before its workers
```

## Set retention

Set how much history the server keeps:

```bash
sqb server --statistics-retention-days 30 --audit-retention-days 730 --snapshot-retention-count 20
```

| Data | Option | Default | Range |
| --- | --- | --- | --- |
| Hourly warehouse statistics | `--statistics-retention-days` | `90` | `1`–`65535` |
| Security audit records | `--audit-retention-days` | `400` | `1`–`65535` |
| Published snapshots per location and target | `--snapshot-retention-count` | `10` | `1`–`65535` |
| Skipped and covered schedule ticks | None | 30 days | Fixed |

Statistics samples older than the horizon disappear from statistics reads at once and are then
deleted in the background.

A security audit record older than the horizon is deleted only when it is no longer needed:

- The webhook in `SQLBUILD_SECURITY_AUDIT_WEBHOOK_URL`, if set, has received it.
- No retained run's retry depends on it. A manual job or rerun request keeps its record while
  the run exists.
- It is not the newest record, so audit page cursors never see a reused position.

Records kept past the horizon for these reasons are reported on stderr as
`Security audit retention: retained past horizon: N` whenever the count changes. A growing count
usually means the audit webhook is failing.

The server keeps the newest published snapshots for each location and target. It deletes an older
snapshot only when no retained run, job, trigger, trigger change or location request uses it, and
deletes its node definitions and SQL text when no other snapshot shares them. Repeating or
interrupting this cleanup is safe.

The scheduler deletes covered and skipped ticks older than 30 days. It keeps each trigger's latest tick and
every tick that started a run. A new schedule, a resumed trigger or a cursor reset catches up only
on the latest missed time, so deleted ticks never come back.

An invalid value stops the server before it opens the control database. Servers that share one
control database delete at the shortest horizon among them and count only their own audit
webhook, so give them the same values and webhook.

## Grant roles to OIDC groups (beta)

With OIDC sign-in, members of an identity-provider group can get a role without a per-person
assignment. Add `groups_claim` and `group_roles` to the JSON file passed to `--oidc-config`:

```json
{
  "origin": "https://control.example.com",
  "issuer": "https://login.example.com",
  "client_id": "orders-control",
  "identities": {"orders-person": "0190c3c1-5a4e-7b8e-9f00-2a7d1c9e4b11"},
  "groups_claim": "groups",
  "group_roles": [
    {"group": "orders-operators", "role": "operator", "location_id": "0190c3c1-6b2f-7c3d-8e44-5f1a2b3c4d5e", "target": null},
    {"group": "orders-readers", "role": "viewer", "location_id": null, "target": null}
  ]
}
```

| Key | Meaning |
| --- | --- |
| `groups_claim` | ID-token claim that lists the person's groups. Required when `group_roles` is set. |
| `group_roles[].group` | Group name exactly as the claim lists it. |
| `group_roles[].role` | `viewer`, `operator`, `developer` or a project role the location publishes. Not `admin`. |
| `group_roles[].location_id` | Limits the role to one location. Required for a project role or a target. |
| `group_roles[].target` | Limits the role to one target in that location. |

Groups grant roles only to people who already have an entry in `identities`; a group never
creates an account. Group roles add to the person's own role assignments.

The server reads groups only from the signed ID token, at sign-in. Each sign-in replaces the
person's groups with the ones in that token:

- Removing someone from a group in the identity provider stops the grant at their next sign-in.
  Until then, all of their sessions use the groups from their most recent sign-in.
- Removing or changing a `group_roles` entry and restarting the server changes access at once,
  without a new sign-in.
- A claim that is missing, is not a list of non-empty names, or is replaced by an overage pointer
  gives no groups.

The server refuses to start when a mapping grants `admin`, scopes a project role or target without
a location, has a blank group, or when `group_roles` is set without `groups_claim`.

Servers that share one control database must use identical OIDC and `group_roles` configuration.
Different configurations on one database are unsupported: the last server to start decides the
group mapping for all of them.

## Inspect published SQL

Sign in with [`sqb login`](/docs/cli/login/), then inspect one exact node in the current
successful publication:

```bash
sqb control sql model:orders \
  --server https://control.example.com \
  --location-id "$LOCATION_ID" \
  --target development
```

The command uses your saved person session and prints JSON. It does not load a local project
or open a warehouse connection. Use `--ca-cert PATH` for an additional trusted PEM certificate.
The node key is exact: `model:orders+` does not expand a selector. Progress and failures go to
stderr; a failed request prints no SQL to stdout. Permission denials include their decision ID.

The equivalent person-authenticated API is a `GET` request to
`/api/control/locations/{location_id}/targets/{target}/nodes/{node_key}/sql`.

Developer or Admin access must cover the requested location and target, or a
[project role](#define-project-roles) must grant `view.sql` on the node. Viewer, Operator and
the configurable default Viewer role do not grant SQL inspection. The response contains the
snapshot ID, exact node key, raw SQL and compiled SQL. Missing SQL fields are `null`; an absent
current publication or node returns JSON `null` after authorization.

SQL inspection does not execute SQL or return Python source, execution artifacts, logs or sample
data. Every successful inspection records an audit entry without copying SQL into it. If the
audit cannot be saved, the request fails without returning SQL. Revocation takes effect on the
next request, including sessions created by [`sqb login`](/docs/cli/login/).

## Sync from the warehouse now

A code location reads what has been built, checks and freshness back from the warehouse when it
starts and after each run the server starts has ended. It does not see a `sqb build` you run on
your own machine until then. To sync now, select **Sync now** on the location's page, or run:

```bash
sqb control sync \
  --server https://control.example.com \
  --location-id "$LOCATION_ID" \
  --target development
```

The command prints `{"applied": true}` when the server has queued the request. The location starts
the sync within a few seconds, and the top bar shows when it last synced. A sync reads the
warehouse and never writes to it. On Snowflake, it skips state tables that haven't changed since
the last sync, so a sync with nothing new doesn't resume the warehouse.

Requesting a sync needs the same access as a connection test: Developer or Admin on the location
and target. Viewer and Operator cannot request one. Every request is recorded in the audit log.

## Skip overlapping runs and retry failures

Declare who owns a job, whether scheduled requests wait for a running copy, and how often a failed
run retries:

```python
from sqlbuild.orchestration import job, on_failure, schedule

nightly_orders = job(
    "nightly_orders",
    description="Orders and their daily totals",
    select="+order_totals",
    owner="Orders team",
    overlap="skip",
    on_failure=on_failure(retries=2, retry_delay_seconds=600),
    schedule=schedule(cron="0 2 * * *", timezone="UTC"),
)
```

| Setting | Values | Default | Effect |
| --- | --- | --- | --- |
| `owner` | Any non-blank text | None | Shown on the job's page and in the job list |
| `overlap` | `queue` or `skip` | `queue` | With `skip`, a schedule tick or sensor request that arrives while a run of the job is queued or running starts no run |
| `on_failure` | `retries` from 1 to 10, `retry_delay_seconds` from 0 to 86400 | None | A failed or partial run reruns its failed and skipped nodes after the delay, until it succeeds or the retries run out |

A skipped tick shows as **skipped** in the trigger's tick log, with the run it yielded to, and
creates no run. A sensor check lists the requests it skipped the same way.

| Sensor watches | A request skipped while the job runs |
| --- | --- |
| Run, node or platform events | Is dropped |
| New source data or stale sources | Is checked again on the next check and starts a run once the job is idle, if the source is still new or stale |
| Custom code | Starts a run once the job is idle if the code returns the same run key again |

Details:

- Runs people start, reruns and backfills always queue, whatever the job's `overlap`.
- A tick that makes up for several missed times, after the scheduler was down or the trigger was
  paused, still queues.
- A retry waits in the queue until its delay ends, and the run list shows it as a rerun of the run
  that failed. Cancelling a run stops its retries.
- A group retries at group level, with the group's own `on_failure`: each retry is one rerun of the
  group's failed and skipped nodes. A member job's `on_failure` applies only when that job runs on
  its own.
- An invalid value fails publication with the job's name, such as
  `job nightly_orders overlap must be queue or skip, not coalesce`.

## Run ad-hoc commands

People with `run.adhoc` can run a `sqb` command on the current publication without declaring a
job. Use the web UI's plan page, or send the command as argument tokens after `sqb`:

```json
{
  "location_id": "0191f0aa-0000-7000-8000-000000000001",
  "target": "development",
  "command": ["build", "--select", "+orders", "--full-refresh"],
  "priority": 0
}
```

`POST /api/control/runs/adhoc/check` with this body is a dry run. It returns the exact nodes the
command selects (`selection`), the nodes it writes (`write_set`), the options the worker receives
(`settings`), and each permission it needs with your decision (`permissions`). `error` explains a
command that can't run whatever your permissions, and `launchable` is `true` when the launch
would be accepted. A dry run queues nothing and records no audit entry.

To launch, `POST /api/control/runs/adhoc` with the same fields plus a new `run_id` and a
`reason`. The response is `{"applied": true}`; sending the same `run_id` again returns
`{"applied": false}` and starts nothing. The server resolves selectors against the current
publication, and the worker runs exactly the resolved nodes, from the project it verified against
that publication; files that change on the location after that check are not used. The target is
always the one in the request.

| Verb | What the worker runs |
| --- | --- |
| `build` | The selected nodes, with their tests and audits |
| `test` | The SQL tests of the selected models |
| `audit` | The audits of the selected nodes, against what is already built |
| `seed` | The selected seeds; other selected nodes are left out |
| `freshness` | The selected sources and every source upstream of the selection |
| Any other verb | Refused |

Only `build` and `seed` write, so `test`, `audit` and `freshness` runs never wait for other runs.
A `test` or `audit` run reports each selected node with the worst result of its tests or audits.

Selectors use the CLI grammar: names, `seed:`, `source:`, `tag:`, `path:` and `test:`, with `+`
for upstream or downstream nodes. Positional selectors work as on the command line.

| Flags | Verbs | Needs |
| --- | --- | --- |
| `--select`, `-s`, `--exclude` | All | `run.adhoc` on every selected node |
| `--full-refresh`, `--start-cursor`, `--end-cursor`, `--start-cursor-ts`, `--end-cursor-ts`, `--start-cursor-int`, `--end-cursor-int` | `build` | `run.rewrite_history` |
| `--allow-snapshot-full-refresh`, `--allow-snapshot-schema-change`, `--allow-table-type-downgrade`, `--allow-retention-decrease` | `build` | `run.rewrite_history` |
| `--warehouse` | All | `run.warehouse`, and the warehouse configured for the target on the location |
| `--max-microbatches`, `--no-load`, `--no-tests`, `--no-audits`, `--no-python`, `--fail-fast`, `--selection-diagnostics`, `--verbose` | `build` | `run.adhoc` |
| `--concurrency` | `build`, `test`, `seed`, `audit` | `run.adhoc` |
| `--test-timeout` | `build`, `test` | `run.adhoc` |
| `--case`, `--inspect` | `test` | `run.adhoc` |
| `--state`, `--fail-on-error`, `--fail-on-stale` | `freshness` | `run.adhoc` |

A priority above 0 also needs `run.prioritise`. Among built-in roles only Admin grants
`run.rewrite_history`, `run.warehouse` and `run.prioritise`. Every other flag is refused with
its reason:

| Refused flags | Reason |
| --- | --- |
| `--vars` | Variables change the published SQL |
| `--defer-to`, `--defer-sources-to`, `--defer-clone-from` | They read another target |
| `--load`, `--reload` | Source loads are not part of ad-hoc runs |
| `--allow-missing-migration-origin` | It can lose data |
| `--no-sql-analysis`, `--no-cache` | Workers verify the published SQL and manage their own cache |
| `--debug` | It prints executed SQL |
| `--since`, `--explain` | They need the worker's Git checkout |
| `--select-file` | It reads a file on the worker |
| `--target`, `--project-dir` and the `--dbt-*` paths | Workers run the published project for the request's target |
| `--json`, `--json-output`, `--event-output`, `--manifest`, `--no-color` | Workers own the run's output |

For an ad-hoc run, the worker checks `--warehouse` against the warehouses the location
configures for the target before any statement runs. An unconfigured warehouse fails the run with
the reason `the requested warehouse is not configured for this target on this location; no
warehouse statement ran`, which the run page shows. A job's own `warehouse` setting is not
checked this way.

## Plan builds

Anyone with `view` on every node of a target can see what a `build` command would do before it
runs. The web UI's plan page does this for every Run button: the location serving the target runs
[`sqb plan --json`](/docs/cli/plan/) on the command's nodes, and the page shows each model's action
and reason, backfills, migrations and warnings. Running the command still needs `run.adhoc`.

A plan reads the server's synced copy of the target's warehouse metadata, not the warehouse, so
planning never resumes a suspended warehouse. The page shows when that copy synced, or that it
hasn't fully synced yet. Each incremental model's range starts where its last successful build
ended and runs to the latest data when the run starts. The run plans again against the warehouse.
These stay unknown until it does:

- source freshness, retention, table types and column rename support;
- sources outside the schemas the server syncs;
- the cursor position of an incremental model with no successful build;
- the range start of an incremental model with lookback, a replay on change, a start override,
  microbatches or a `cursor_start` past its last build;
- whether a start set with `cursor_start_max_ahead` sits too far ahead;
- the columns of an expression source whose SQL changed since it was last described, which the
  plan takes as declared.

Over the API, queue a plan, then read it until `result_json` is set:

```json
POST /api/control/locations/{location_id}/targets/{target}/plans
{ "request_id": "0191f0aa-0000-7000-8000-0000000000a1", "command": ["build", "--select", "+orders"] }

GET /api/control/locations/{location_id}/targets/{target}/plans/{request_id}
```

`result_json.outcome.kind` is `plan`, with the `sqb plan --json` document in `document`, or
`superseded` when the location's project files changed while it planned; plan again. A plan never
appears in Runs and never connects to the warehouse. In `document`, `synced_copy` holds
`synced_at` (`null` until the copy has fully synced), `cursor_window_starts` and
`unknown_until_run`.

| Limit | Value |
| --- | --- |
| Verbs | `build` only |
| Flags | Those accepted for an [ad-hoc run](#run-ad-hoc-commands); `--warehouse` and flags `sqb plan` doesn't take, such as `--fail-fast`, don't change the plan |
| Location | A `sqb location serve` for the target that reported in the last 90 seconds |
| Plans waiting | One per person and four per target |
| Expiry | 10 minutes |
| Plan size | 8 MiB |

Only the person who asked can read a plan. Python source and dependency diffs are left out unless
they also have `view.sql` on every node, and secrets in warehouse error text are redacted.

## Define project roles

Put project roles in `roles.toml` at the project root. `sqb location publish` resolves each
grant's node selectors against the published project:

```toml
[roles.orders_support]
description = "Answer order questions"

[[roles.orders_support.grants]]
nodes = ["tag:orders"]
permissions = ["view.sql", "run.adhoc"]

[[roles.orders_support.grants]]
nodes = ["tag:orders,tag:pii"]
permissions = ["view.evidence"]
```

| Rule | Behaviour |
| --- | --- |
| Selectors | Same grammar as a job's `select`; an unknown tag or name fails publication |
| No matching nodes | Publication succeeds with a warning; the grant gives nothing |
| Permissions | Any non-administrative action; `user.manage`, `role.assign` and `audit.view` are rejected |
| Runs | `job.run`, `run.rerun` and `run.rewrite_history` need the permission on every node the run writes; an [ad-hoc command](#run-ad-hoc-commands) needs `run.adhoc` and its flags' permissions on every node it selects; a priority above 0 also needs `run.prioritise` |
| Triggers | `trigger.toggle` and `sensor.reset_cursor` need the permission on every node the trigger's job writes |
| Listings | The catalog, statistics and run list need `view` on every node of the current publication; partial coverage is denied, not filtered |
| Several roles | Grants add up across a person's roles |

Assign a project role with `POST /api/admin/roles`, using the role key as `role`. Each
publication replaces the location's project roles: new and changed grants apply at once, and
removed roles stop applying. A selector covers newly matching nodes as soon as they are
published. Each change appears in the publication's change list as `role:<key>`. A denial names
only the missing permission, such as `missing view permission for this target`, and its decision
ID. It names no nodes, and an unknown location, job, trigger or run is refused with the same
response. The security audit event for that decision ID lists the nodes the request was missing.
