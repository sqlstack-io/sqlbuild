Run the control API, the scheduler and a code location for the project in the current directory,
then open the web UI at the address in the ready box:

```bash
sqb dev
```

```text
sqb dev  shop · target dev · sqb 0.256.0
✓ Opened control store    0.0s   sqlite
✓ Started UI server       0.1s   http://127.0.0.1:8000
✓ Started scheduler       0.0s   triggers start paused
✓ Discovered project      0.6s   4 python nodes, 38 models
✓ Compiled project        0.4s
✓ Published snapshot      0.1s   snapshot 01a1d7ff
✓ Connected warehouse     0.3s   duckdb
╭─ ready ────────────────────────────────────────────────────────────────────╮
│ UI         http://127.0.0.1:8000                                           │
│ Project    shop · ~/src/shop · target dev                                  │
│ Warehouse  duckdb · database /work/shop/warehouse.duckdb                   │
│ Triggers   3 paused                                                        │
│ Env file   .env · 2 variables · edit it, then press r to reload            │
╰────────────────────────────────────────────────────────────────────────────╯
keys  o open UI · l full log · r recompile · q quit
```

Each step shows a spinner and its elapsed time while it runs, and its finished line stays on
screen. The live part of the screen, the running steps and the key line, is never taller than the
terminal. The location compiles the project, runs its [Rules](/docs/concepts/rules), and publishes
it to the server. When you save a model, orchestration file or other project input, it compiles
and publishes again, so the UI and the next run use the new version. Each change, publication,
failure and run gets one line above the key line, wrapped rather than cut off. A compile error or
a Rule finding leaves the previous version published and is shown in full: what failed, where, why
and how to fix it.

## Options

| Option | Default | Effect |
| --- | --- | --- |
| `--port` | `8000` | Port to listen on. `0` picks a free port |
| `--host` | `127.0.0.1` | IP address to listen on; see [Open it to a proxy or a network](#open-it-to-a-proxy-or-a-network) |
| `--allow-host` | None | Also accept this name in `Host` and `Origin`; repeat it for more names |
| `--target` | The configured target | Target to compile and run |
| `--control-store-url` | `.sqlbuild/control.sqlite3` in the project | Control store URL or path |
| `--no-scheduler` | Off | Serve and reload without running scheduled work |
| `--triggers` | Off | Keep each trigger's default status and your changes to it, instead of pausing every trigger at start-up |
| `--plain` | Off, unless stdout or stderr is not a terminal | Print appended lines instead of redrawing the screen; see [Plain output](#plain-output) |

## Open it to a proxy or a network

By default `sqb dev` listens on `127.0.0.1` and answers only requests whose `Host`, and `Origin`
when there is one, are local. That stops other websites in your browser from using the session,
which has no sign-in.

:::danger
With `--host` beyond loopback or with `--allow-host`, anyone who can reach that address or name has
full access without signing in and with your credentials: they can change and run what the project
can, against your warehouse. These options don't identify callers. A client other than a browser
can send any `Host` it likes, so only the network or the proxy limits who gets in.
:::

Use them only for your own session, or for one shared on purpose with people you would hand your
credentials to, on a trusted network. Use [`sqb server`](/docs/cli/server/) for anything else: when
people need their own accounts or roles, or the address is reachable by anyone you don't trust.

Behind a reverse proxy on the same machine, allow the name people browse to:

```bash
sqb dev --allow-host control.example.com
```

On a trusted network without a proxy, listen on the network and allow each name or IP address that
people browse to:

```bash
sqb dev --host 0.0.0.0 --allow-host buildbox.example.com --allow-host 192.0.2.10
```

An allowed name works over HTTP and HTTPS on the default ports and on `sqb dev`'s own port. For a
proxy on another port, include it: `--allow-host control.example.com:8443`. A name given with a
port works only on that port. Write names without a scheme or path; there are no wildcards. Every
other name stays refused, including when listening on `0.0.0.0`, so other websites and DNS
rebinding are still blocked. When either option opens the session, a **No sign-in** warning at
start-up and the ready box's **Access** row say who gets in.

## Set provider secrets

`sqb dev` loads the project's [env file](/docs/concepts/project-configuration#env-file), `.env`
by default, when it starts, and the **Env file** row in the ready box says how many variables
it set. After editing the file, press `r`: the location reads it again and restarts its Python
interpreter when a value changed, so the next compile and run use the new values. Variables set
in the shell that started `sqb dev` still win.

While a provider is missing secrets that the target doesn't
[allow to be missing](/docs/concepts/project-configuration#allowed-missing-secrets), `sqb dev`
keeps running and prints a warning with each field's file and line, the variable it reads, the
nodes that need the provider (the first five, then a count) and the fix, never a value:

```text
⚠ warn   1 provider has missing secrets                          missing secret
  at     python/providers/region.py:9   region_token  ← REGION_TOKEN
         python/providers/region.py:10  region_code   ← REGION_CODE
  why    runs that use it stop at the provider check, before the warehouse; 2
         nodes need it (raw_regions, stg_regions)
  fix    set them in .env and press r, or set them in the environment you
         start sqb dev from, then quit and run sqb dev again
```

`r` picks up an edit to the env file, which the fix names when the target uses another one. It
can't pick up a variable exported in a shell afterwards: for that, quit and run `sqb dev` again.

The warning is printed again when the missing variables change, and a **Secrets missing** row stays
above the keys meanwhile. Once the next publication finds every secret set, the row clears and a
`Secrets set` line says so.

## Sign in to the warehouse

Once the first version is published, `sqb dev` connects to the target's warehouse in the
foreground. A client that asks for a password, a code or a browser sign-in asks once, in a
**sign in** block above the running steps, and every later connection in the session reuses that
sign-in. What you type goes to the client, which reads it on its own terminal, so prompts that
read `/dev/tty` work too. A prompt that hides what you type, such as a password prompt, keeps it
hidden on the screen, in the log and in `--plain` output; other prompts show what you type.
Ctrl+C still stops `sqb dev`. `sqb dev`
waits for the sign-in as long as it takes, and the block shows how long it has waited.

If the first connection fails, `sqb dev` shows the error and stops with exit status 2; run
`sqb debug` to test the connection on its own. The ready box's Warehouse line names the adapter
and the connection's account or host, authentication, role and warehouse or database. The
location reads warehouse history once the connection succeeds.

## Keys

| Key | Effect |
| --- | --- |
| `o` | Open the UI in your browser |
| `r` | Read the [env file](/docs/concepts/project-configuration#env-file) again, then compile and publish |
| `l` | Show or hide the detailed log, the latest 500 lines |
| `q` | Stop |
| Ctrl+C | Stop; a second Ctrl+C stops at once |
| Ctrl+\\ | Stop at once, without cancelling runs |

Ctrl+Z is not supported: `sqb dev` does not suspend. Stop it with `q` or Ctrl+C instead.

## Republish from a script

[`sqb location republish`](/docs/cli/location#republish) asks the location `sqb dev` serves to
compile and publish again, the same as pressing `r`: every discover function runs. Use the
address and the location ID from the ready box. `sqb dev` has no sign-in, so `SQLBUILD_API_KEY`
can be any value; the command needs one to call over `http://`:

```bash
SQLBUILD_API_KEY=local sqb location republish --server http://127.0.0.1:8000 \
  --location-id 01a1d7ff-0b3a-7631-ba35-e44d44d072f2 --target dev --wait
```

A `curl` request to the [republish endpoint](/docs/cli/location#republish) needs no key either.

## Stop

`q`, Ctrl+C, SIGINT, SIGTERM and SIGHUP stop `sqb dev` at any point, including while it reads the
configuration, opens the control store, compiles, connects or waits for a sign-in. A stop before
`sqb dev` is ready ends with `sqb dev stopped (interrupted) before it was ready`.

When no run is in flight, each service stops with one line, and anything still running after
about a second is killed, the code location included. When runs are in flight, `sqb dev` cancels
them first, also when a service fails after it was ready: each worker cancels its running
statements, records the run as cancelled and releases its claims, as it does for a cancel from
the UI. This takes up to 30 seconds, then whatever is left is killed. Ctrl+C again, or Ctrl+\\,
stops at once:

```text
· Cancelling run orders_job… 2 running nodes (Ctrl+C again to force)
· Cancelled run orders_job  2 running nodes cancelled   1.2s
· Stopped scheduler       0.0s
· Stopped UI server       0.1s
· Stopped code location   0.3s
· sqb dev stopped (interrupted)  ran 42m 10s   1.6s
```

Each local worker runs in its own process group, which is stopped as a whole, so nothing a worker
started is left running. The terminal is put back as it was, and the last line says how the
session ended.

| Exit status | Meaning |
| --- | --- |
| `0` | Stopped with `q` |
| `1` | A service failed after `sqb dev` was ready |
| `2` | `sqb dev` did not start, for example because the configuration is invalid or the first warehouse connection failed; the screen says why |
| `129` | SIGHUP, or the terminal closed |
| `130` | Ctrl+C or SIGINT |
| `143` | SIGTERM |

## Plain output

With `--plain`, on Windows, with `TERM=dumb`, when `CI` or `SQLBUILD_NO_PROGRESS` is set, or when
stdout or stderr is not a terminal, `sqb dev` appends lines and never redraws: no spinners, no
keys and no colour. Only finished steps are printed. `NO_COLOR` turns colour off and nothing else.

```text
sqb dev  shop · target dev · sqb 0.256.0
✓ Opened control store    0.0s   sqlite
✓ Started UI server       0.1s   http://127.0.0.1:8000
✓ Discovered project      0.6s   4 python nodes, 38 models
✓ Published snapshot      0.1s   snapshot 01a1d7ff
✓ Connected warehouse     0.3s   duckdb
✓ ready  http://127.0.0.1:8000
  warehouse  duckdb · database /work/shop/warehouse.duckdb
  location   01a1d7ff-0b3a-7631-ba35-e44d44d072f2
  triggers   3 paused
  env file   .env · 2 variables · edit it, then press r to reload
14:20:31 ▸ run orders_daily  started manually
```

Warnings, such as a failed warehouse read, a stopped warehouse sync or unset provider secrets, are
printed as warning blocks.

When stdout is redirected, it receives one JSON record per published version.

## Run scheduled jobs locally

Triggers start paused, so a schedule never runs on your machine by accident. Resume a trigger in
the UI to let it run, or start with `--triggers` to keep the status each trigger was declared with:

```bash
sqb dev --triggers
```

## Warehouse cost

While it runs, the location reads what has been built back from the warehouse after each
publication, after each run and at least every 30 minutes. In `sqb dev` every saved change is a
publication. These reads never write to the warehouse; what they cost depends on the adapter:

| Adapter | What a sync costs |
| --- | --- |
| Snowflake | A sync with nothing new does not resume a suspended warehouse. The first sync after each publication or restart resumes it, which bills Snowflake's 60-second minimum |
| BigQuery | Every sync runs one billed query job per state table, each charged at least 10 MB on demand |
| Databricks | Every sync runs SQL on the SQL warehouse, which starts it if it is stopped |
| PostgreSQL, SQL Server, ClickHouse, MotherDuck | No cost from SQLBuild itself. A serverless host that pauses when idle wakes for each sync |
| DuckDB, SQLite | None: the warehouse is a local file |

To read less often, set `[control] sync_at_least_every`, as described in
[Sync from the warehouse now](/docs/cli/server/#sync-from-the-warehouse-now). `"off"` stops the
timed reads but not the read after each publication or run.

## Details

- `sqb dev` needs no sign-in and listens only on loopback unless you
  [open it up](#open-it-to-a-proxy-or-a-network). Use [`sqb server`](/docs/cli/server/) for a
  server other people or machines connect to.
- The control store keeps runs, trigger changes and history between sessions. Delete
  `.sqlbuild/control.sqlite3` to start again from nothing.
- The location is named after the project, the `name` in `sqlbuild_project.toml`. When the
  control store already has a location with that name, for example from another target of the
  same project, it gets ` (2)`, then ` (3)`, and so on.
- The UI is ready once the project compiles and publishes. The location then reads SQLBuild's
  history from the warehouse; plan previews, history and costs show
  **Syncing warehouse history** until that first sync completes. See
  [Follow a sync](/docs/cli/server#follow-a-sync).
- The control store keeps the newest 5 builds of each node and results of each check that it copies
  from the warehouse; older ones are deleted and the file shrinks. See
  [retention](/docs/cli/server#set-retention).
- When a service fails without an explanation on screen, `sqb dev` prints the last log lines
  above its result line.
