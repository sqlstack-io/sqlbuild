---
title: "Selectors"
description: "Target specific models, paths, tags, or DAG subsets with select and exclude flags."
---

Selectors let you scope commands to specific subsets of your project. They work with `plan`, `build`, `test`, `audit`, `seed`, `clone`, and `diff`.

## Basic usage

```bash
sqb build daily_revenue
sqb build daily_revenue customer_status_snapshot
sqb build --select daily_revenue
sqb build --exclude stg_customers
```

Selectors can be written as positional arguments on `compile`, `plan`, `build`, `test`, `seed`, `freshness`, `audit`, and `check`, or with `--select` (or `-s` for short) on any command that selects. Both forms accept one or more names, can be combined, and are unioned. `--exclude` subtracts from the selected set.

When no `--select` is provided, all models are selected.

## Selector types

### Name

Select a single resource by name:

```bash
sqb build --select fact_orders
```

Bare names accept glob patterns. This selects every resource whose name starts with
`intermediate_`:

```bash
sqb build --select "intermediate_*"
```

Name globs compose with graph expansion. For example, `+intermediate_*` selects every matching
resource and all of their upstream dependencies. Quote patterns in shell commands so your shell
does not expand `*` against files in the current directory.

### Tag

Select all models with a specific tag:

```bash
sqb build --select tag:staging
sqb build --select tag:acceptance
```

### Path

Select all models under a directory path:

```bash
sqb build --select path:sql/models/marts
sqb build --select sql/models/marts
sqb build --select path:sql/models/intermediate
```

Any name containing `/` is treated as a path selector, so `path:sql/models/marts` and a bare `sql/models/marts` work the same way. Path selectors require an explicit root directory: `sql/models/` for SQL models or `python/nodes/` for Python nodes. Nested paths work too: `sql/models/staging/orders` or `python/nodes/exports`.

### Seed and source

```bash
sqb build --select seed:waffle_types
sqb build --select source:raw__orders
```

### Kind

Select every node of one kind:

```bash
sqb build --select kind:seed
sqb build --select "kind:model,path:sql/models/marts"
sqb build --select +kind:asset
```

The kinds are `model`, `source`, `seed`, `udf`, `table_fn`, `asset`, `loader` and
`check`, as the server's catalog names them, and `function`, which selects both `udf` and
`table_fn`. Kind selectors compose with `+`, `,` and `--exclude`
like tag selectors. An unknown kind is an error that names the closest kinds, and a kind your
project has no nodes of is an error, as an unused tag is.

### Job

Select the SQL and Python nodes a [job or job group](/docs/concepts/orchestration) builds. Job names are globally
unique, so a bare name works; `job:` is the explicit form and accepts glob patterns:

```bash
sqb build nightly_orders_job
sqb build --select job:nightly_orders_job --exclude order_totals
sqb build --select "job:nightly_orders_job,tag:finance"
```

A job selects its own `select` minus its own `exclude`. A job group selects the union of its jobs.
Naming a job also applies its settings to its nodes; see
[Settings when a build names a job](/docs/concepts/orchestration#settings-when-a-build-names-a-job).
A job or job group declared with `targets` is selectable only when the command's target is one of
them, as on the server.
Job selectors compose with `+`, `,` and `--exclude` like any other selector. A job's own selection
cannot name another job, and path-between selectors cannot start or end at a job.

SQLBuild reads job and job group files without running project Python.

### Unit test

`sqb test` and `sqb build` select SQL unit tests by name. Test names are globally unique, so a bare
name works; `test:` is the explicit form and accepts glob patterns:

```bash
sqb test order_status_rules
sqb test "test:orders_*" stg_customers
```

Test selectors are unioned with other selectors and cannot use `+` or `,`. Other commands reject
them with `S013`.

### Audit

`audit:` selects an audit by name, the end-of-build singular audits included, and accepts glob
patterns:

```bash
sqb build audit:orders_match_payments
sqb audit "audit:not_null_*"
sqb build daily_revenue audit:revenue_reconciles
```

An audit has no upstream or downstream nodes, so `+` adds nothing to it, and it composes with `,`
and `--exclude` like any other selector. An audit selected by name runs whether or not its target
is in the selection: when the build doesn't build the target, the audit runs after everything else,
against the target as it is. `sqb plan` lists audits selected by name under `Audits`, and its
`--json` output under `audits`.

`plan`, `build`, `test`, `audit` and `check` accept `audit:`; other commands reject it with `S010`.

## Graph expansion

### Upstream

Select a model plus all its upstream dependencies:

```bash
sqb build --select +daily_activity_rollup
```

### Downstream

Select a model plus all its downstream dependents:

```bash
sqb build --select fact_orders+
```

### Bidirectional

```bash
sqb build --select +fact_orders+
```

Graph expansion works with all selector types:

```bash
sqb build --select +tag:marts
sqb build --select path:sql/models/staging+
```

## Path-between selectors

Select all models on every path between two nodes:

```bash
sqb build --select fact_orders~daily_activity_rollup
```

With endpoint expansion:

```bash
sqb build --select +fact_orders~daily_activity_rollup+
```

This selects:
- All upstreams of `fact_orders`
- Every model on the path between `fact_orders` and `daily_activity_rollup`
- All downstreams of `daily_activity_rollup`

This is useful for rebuilding a specific slice of the DAG without manually listing every model in between.

## Intersection

Use commas to intersect selector results:

```bash
sqb build --select "tag:staging,path:sql/models/finance"
```

This selects only models that match *both* conditions - in this case, models tagged `staging` that are also under the `sql/models/finance` directory.

Graph expansion applies to the part it is written on, before the parts are intersected.
`+orders,kind:source` selects `orders` and everything upstream of it, then keeps only the sources:
the sources `orders` reads. `kind:source,+orders` means the same. Spaces separate selectors, whose
results are unioned, so `tag:finance kind:seed` selects nodes tagged `finance` and every seed.

## Combining select and exclude

```bash
# Build all marts except daily_revenue
sqb build --select path:sql/models/marts --exclude daily_revenue

# Build everything upstream of fact_orders, excluding staging models
sqb build --select +fact_orders --exclude tag:staging
```

## Selecting from a past run

Three selectors select from a run that already happened:

| Selector | Selects |
| --- | --- |
| `run:<id>` | Every node the run selected |
| `failed:<id>` | The nodes that failed, were cancelled or never ran, and the audits that failed, not counting ignored audit failures |
| `skipped:<id>` | The nodes the run skipped |

They compose like any other selector, so `failed:<id>+` reruns what didn't succeed and everything
downstream of it, and `run:<id> --exclude skipped:<id>` repeats what the run didn't skip:

```bash
sqb plan failed:20261125T142600Z_1732548e8aea+
sqb build failed:20261125T1426+
sqb build model_a model_b failed:20261125T1426+
```

The last command builds `model_a` and `model_b` too, for example when a failed audit read them
and they don't exist in the target yet.

`<id>` is the run's full ID or a prefix of at least 8 characters that only one run starts with;
wildcards are not accepted. A prefix that more runs start with is an error that lists them.

Without `--server`, the run comes from the project's local [Recall](/docs/cli/recall) history,
which needs the default SQLite store. To list the latest local runs:

```bash
sqb recall query "SELECT run_id, MIN(occurred_at) AS started FROM events
  WHERE run_id IS NOT NULL GROUP BY run_id ORDER BY started DESC LIMIT 5"
```

With `--server`, `--location-id` and an [`sqb login`](/docs/cli/login) session, the run comes from
the server's runs of that location on the command's target, as the web UI shows them:

```bash
sqb plan failed:0192c1a4+ --server https://control.example.com --location-id <uuid>
```

`plan`, `build`, `test`, `audit` and `check` read past runs; other commands reject run selectors with
`S010`.

## Error handling

Unknown resource names, name patterns with no matches, empty paths, and malformed selectors produce
clear error messages:

```
error[S007]: unknown selector name 'nonexistent_model'
error[S007]: unknown selector name 'missing_*'
error[S009]: no models found under path 'sql/models/nonexistent'.
error[S000]: no SQL resources or Python nodes found with tag 'nonexistent_tag'
error[S007]: unknown node kind 'modle'
error[S003]: path selector 'fact_orders~' requires names on both sides of '~'
error[S013]: selector 'order_status_rules' selects a unit test; only `sqb test` and `sqb build` accept unit-test selectors
error[S007]: unknown audit name 'orders_match_payment'
error[S010]: selector 'failed:20261125T1426' selects from a past run; only plan, build, test, audit and check read past runs
```

A run ID that is too short, names no run, or starts more than one is refused before anything is
planned:

```
error[S000]: run ID '2026112' is too short: give the full ID or at least 8 characters of it
error[S000]: no run '20261124' in the local Recall history
error[S000]: run ID '20261125' is ambiguous: it starts 20261125T142600Z_1732548e8aea, 20261125T153329Z_746e30e62302; give more of the ID
```

Unknown names suggest the closest selectable names, including unit tests:

```
error[S007]: unknown selector name 'order_status_rule'
  = help: did you mean 'order_status_rules'?
```

If a path selector omits the root directory, SQLBuild asks for the explicit form:

```
error[S012]: path selectors require an explicit root: use 'sql/models/' or 'python/nodes/'
```
