---
title: "Model migrations"
description: "Keep a renamed model's history, and keep its old name working for a while."
---

Rename a model with `sqb rename stg_orders orders`. On the next build, SQLBuild moves the existing
table to the new name and carries on building it incrementally, so no history is lost and nothing is
backfilled. The old name keeps working as a view for 30 days.

```bash
sqb rename hourly_order_activity order_activity_by_hour
sqb plan
```

```text
Migrations (1)
└── order_activity_by_hour  migrate  dev.hourly_order_activity -> dev.order_activity_by_hour
    ├── compatibility  compatible
    ├── transfer  physical copy, promote by transactional rename
    └── old name  dev.hourly_order_activity
        ├── view  until 2026-11-06
        └── old table  archived
```

This matters most for incremental and snapshot models, whose history the source data may no longer
reproduce. Table and view models are rebuilt under the new name, but they keep their identity for
change detection, and their old name keeps working too. To rename a column instead, see
[Column migrations](/docs/concepts/models/column-migrations).

## Declaring a migration

[`sqb rename`](/docs/cli/rename) and `sqb mv` rename or move a model, update every reference to it,
and write `migrate_from` into the model's header. You can also write it yourself, naming the old
model:

```sql
MODEL (
  description "One row per order",
  materialized incremental,
  migrate_from stg_orders,
  cursor order_date,
  ...
);
```

Use `schema.name` when the old relation is in another schema of the same database.

On the next build, SQLBuild copies the old relation to the new name, records the move, and builds
the model incrementally from there. There is no first-run rebuild, and the rename alone causes no
`replay_on_change` replay. After the model builds, the old relation is archived and a view takes its
name (see [Old names](#old-names)).

A rename usually comes with other edits, such as a changed filter. The plan still recognises the
rename and lists the model as `Renamed` with its query diff. The query change follows the model's
own `replay_on_change`, and downstream models are not replayed because of the rename; see
[Replay decisions](/docs/concepts/planning/replay-decisions).

Once the move is recorded, `migrate_from` has no further effect, and SQLBuild tells you it can be
removed. Keep it until every target that needs the move has built.

## Decisions

`sqb plan` shows the decision for every migration:

| Decision | Meaning |
|----------|---------|
| `migrate` | The new relation doesn't exist. Move the old one's data to it. |
| `done` | The move is already recorded. Nothing to do. |
| `redo` | The new relation exists with no build history and no recorded move. An interrupted migration leaves this. Move it again. |
| `superseded replace` | The new relation was the origin of the latest recorded move, for example after renaming a model back. Replace it with the newer data. |
| `forced replace` | The new relation has its own build history and `migrate_force true` is set. Replace it. |
| `conflict` | The new relation has its own build history. The build stops (`M103`) until you set `migrate_force true` or remove `migrate_from`. |
| `origin missing` | The old relation doesn't exist and no move was recorded, for example on a fresh target. The plan warns (`M102`) and the model builds fresh. |

On a target where the old name was never built, `origin missing` is normal. A target can ask for
confirmation or stop the build instead; see [Missing migration origins](#missing-migration-origins).

If SQLBuild built the old relation in this target but can't see it now, the build always stops with
`M102`: the connection may lack permission, or the relation was dropped outside SQLBuild. Restore
access, or remove `migrate_from` to build fresh on purpose.

The old and new relations must be compatible under the model's `on_schema_change` rules; otherwise
the build stops (`M104`). `migrate_force true` only affects the `conflict` case and is safe to leave
in the header.

Table and view models only see `migrate`, `done` and `origin missing`, because nothing is replaced.
`migrate_force` on a table or view model is a compile error. In `sqb plan --json`, their decision is
`renamed`.

### Missing migration origins

On a target that never built the old name, such as a fresh development schema, there is nothing to
move. The target's `missing_migration_origin` decides what the build does:

| Value | Behavior |
|-------|----------|
| `allow` | Default. The plan warns (`M102` for models, `M109` for columns) and the model builds as if `migrate_from` were absent. |
| `require_confirmation` | The build asks on a terminal and stops otherwise. Pass `--allow-missing-migration-origin` to confirm in a non-interactive run. |
| `deny` | The build stops with `M102` or `M109`. Use it where a missing origin means the wrong target or a lost table. |

```toml
[targets.prod]
missing_migration_origin = "deny"
```

`sqlbuild_local.toml` can set it for a target too. `sqb dbt run` and `sqb dbt build` follow it but
have no confirmation flag: they ask on a terminal and stop otherwise. In a non-interactive dbt run,
build the affected models with `sqb build --allow-missing-migration-origin` and leave them out of
the dbt selection, or set the target to `allow`.

## Automatic discovery

A model you rename by hand, without `migrate_from`, is still found when its logic is unchanged. If a
selected model has never been built and exactly one removed model has the same query and
configuration, SQLBuild migrates it automatically. Renamed upstream models are matched first, so a
renamed chain of models moves together.

Discovery never guesses. If more than one removed model matches, SQLBuild warns (`M107`) and builds
from scratch; declare `migrate_from` to choose. An explicit `migrate_from` always wins. Discovery
covers renames within the project's schemas; use `migrate_from` to move a model to another schema.

## Old names

A rename breaks every query outside the project that reads the old name: dashboards, notebooks,
other teams' jobs. So after the renamed model builds, SQLBuild archives the old relation and creates
a view at the old name that reads the new one. The view gets the privileges that were granted on the
old relation; nothing new is granted.

```text
Migrations (1)
└── daily_revenue  migrate  analytics.revenue -> analytics.daily_revenue
    ├── transfer  rebuild (table)
    └── old name  analytics.revenue
        ├── view  until 2026-10-28
        ├── columns  amount <- revenue
        ├── grants  copied from the old table
        └── old table  archived
```

If columns were renamed, the view shows them under their old names, for example
`SELECT order_id, revenue AS amount FROM analytics.daily_revenue`. Incremental and snapshot models
alias every recorded [column migration](/docs/concepts/models/column-migrations). A table or view
model that declares `migrate_from` can name old columns the same way, as
`revenue (migrate_from amount)`; this only aliases the column in the view.

The view expires after 30 days. Then [janitor](/docs/cli/janitor) drops it;
`sqb janitor --drop-old-name-view analytics.revenue` drops it earlier. Change the default for the
project, or turn views off with `false`:

```toml
[migrations]
old_name_views = "7d"
```

A model header overrides this with `old_name_view 7d` or `old_name_view false`. A move keeps the
retention it had when it was recorded.

No view is created when views are off, when the old relation wasn't built by SQLBuild, when another
model builds at the old name, or when the old name is itself a view from an earlier rename. The plan
then shows `left for janitor` and the reason, and janitor archives the old relation once it is no
longer part of the project.

### Privileges by adapter

| Adapter | Privileges copied to the view |
|---------|-------------------------------|
| Snowflake | `SHOW GRANTS` on the archive, replayed to roles and database roles, keeping `WITH GRANT OPTION`. `OWNERSHIP`, grants to shares, and privileges that don't apply to views are skipped |
| PostgreSQL | Table and column privileges, including grants to `PUBLIC` and `WITH GRANT OPTION`. The owner's own privileges are not copied |
| BigQuery | Table IAM role bindings from `INFORMATION_SCHEMA.OBJECT_PRIVILEGES`, replayed with `GRANT` |
| Databricks | Unity Catalog grants on the table that apply to views, such as `SELECT`. `OWN`, `MODIFY`, and inherited catalog or schema grants are skipped |
| SQL Server | Object and column permissions, including `DENY` and `WITH GRANT OPTION`, that apply to views |
| DuckDB, MotherDuck | No object privileges exist |

On BigQuery, a view reads its tables with the permissions of whoever queries it. A principal that
could read the old table also needs read access on the new one. SQLBuild doesn't grant it and
doesn't create authorized views; the build warns with `M118` and names the principals.

### Code inside the project

The view is for consumers outside the project. Project code must use the new name:

- Python nodes, hooks and loaders whose literal SQL names the old name fail with `P008`. SQL models
  that read it through `__ref` are unaffected, since `__ref` resolves the new name.
- A new model named like a live view stops the build with `M114`, which names the view and its
  expiry. Drop the view early with janitor, or choose another name.

## Adapter support

| Adapter | Copy | Promotion |
|---------|------|-----------|
| Snowflake | Zero-copy clone with `COPY GRANTS`. Transient → permanent is a physical copy, because Snowflake can't clone a transient table into a permanent one. | `ALTER TABLE … SWAP WITH` for an existing destination; rename for a missing one |
| BigQuery | `CREATE TABLE … CLONE`, or `CREATE TABLE … COPY` when BigQuery refuses the clone | Two renames; the destination is briefly missing between them, and an interrupted run recovers on retry |
| Databricks | `DEEP CLONE` | Two renames, as for BigQuery |
| PostgreSQL, SQL Server, DuckDB, MotherDuck | Physical copy | Renames and the migration record in one transaction |

## Previewing another target

`sqb plan --as <target>` compiles the project for another target, such as production, and shows its
migration decisions using your current connection. It only inspects; nothing is written.

## Details

- **How a move runs.** The old relation is cloned or copied into a staging table named
  `_sqb_archive__<UTC timestamp>__migration_stage__<name>`. The staging table is checked for its
  columns, table type and, for a physical copy, row count. It is then swapped in as the destination.
  A destination that already existed is kept as `_sqb_archive__<UTC timestamp>__migration_previous__<name>`.
  The move is recorded, the model builds, and only then is the old relation archived as
  `_sqb_archive__<UTC timestamp>__migration_origin__<name>`.
- Staging and replaced tables use the [janitor](/docs/cli/janitor) archive format, so janitor
  deletes an abandoned one after `archive_retention_days`. A staging table left by an interrupted
  run is never reused. Don't run janitor at the same time as a build in the same schema.
- Archiving the old relation, creating the view and copying grants commit in one transaction on
  DuckDB, MotherDuck, PostgreSQL and SQL Server. On Snowflake, BigQuery and Databricks each step is
  recorded after it runs, and a re-run resumes from the first unrecorded step. A failure is reported
  as `M117`; re-run the build.
- Column privileges are copied to the view's column of the same name, which is the old name when the
  view aliases a renamed column. A privilege on a column the view doesn't expose is not copied.
- After it is created, the view's own privileges are what counts. When SQLBuild redefines the view,
  it reads its privileges first and restores them afterwards, so a privilege you revoke stays revoked
  and one you grant is kept. This also undoes privileges that PostgreSQL `ALTER DEFAULT PRIVILEGES`
  or Snowflake future grants would add. Ownership is never changed.
- On Snowflake, BigQuery, Databricks, DuckDB and MotherDuck, views read tables by name, so a build
  redefines the view only when its SQL would change. PostgreSQL views are bound to the table, so
  SQLBuild re-points them in the same transaction whenever the table is replaced, and other views
  that depend on the destination are re-pointed too, keeping their options, owner and grants.
  A view whose columns no longer fit is dropped and re-created with its privileges, which fails if
  another view depends on it. Materialized views are not re-pointed.
- On PostgreSQL, views outside SQLBuild that read the old relation follow it into the archive and
  keep reading its old data; the build warns with `M115` and names them. Re-create them against the
  old name or the new relation.
- BigQuery can't rename views, so an old view model is re-created under the archive name with its
  IAM bindings, then dropped.
- A recorded view that no longer exists is not re-created by a build; janitor records it as dropped.
- Run the same SQLBuild version for `sqb janitor` as for builds. An older janitor doesn't recognise
  compatibility views and archives them as stale relations.
- In `sqb plan --json`, each migration has an `old_name` object with `action` (`archive_and_view`,
  `view_only`, `live` or `none`), `view`, `reads`, `expires_at`, `column_aliases`, `grants_copied`
  and `reason`. The top-level `old_names` list also includes steps that resume an earlier move.
- Discovery ignores the model's own name, CTE and table alias names, comments, formatting and
  storage-only settings. A model already moved on by a recorded migration is not a candidate, so a
  model renamed several times matches its latest table. Relations without a stored fingerprint are
  not matched. Renamed tables and views are recorded as `renamed` events.
- Moves are recorded in an append-only `_sqlbuild_migrations` table in the destination schema, and
  old-name steps in `_sqlbuild_old_name_views`. A missing record means the move may be partly done;
  re-running recovers through the decisions above.
