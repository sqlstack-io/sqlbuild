The `materialized` field selects how a model becomes a warehouse relation.

## View

Creates or replaces a database view on each build:

```sql
MODEL (description "One row per order", materialized view);

SELECT id AS order_id, customer_id, status
FROM __source("raw__orders")
```

Views are checked at compile time only; SQLBuild doesn't add runtime casts or contract checks to a view.

## Table

Builds the new table in a staging table, checks its types and contract, runs blocking audits, and only then replaces the old table.

```sql
MODEL (description "One row per order", materialized table);

SELECT customer_id, COUNT(*) AS total_orders
FROM __ref("stg_orders")
GROUP BY customer_id
```

Set `[settings] table_promotion_mode = "immediate"` to build straight into the destination and audit afterwards. Immediate promotion can't enforce declared types or `contract enforced`. A model with `contract enforced` is a `K011` compile error; a model with declared types fails when it builds.

## Incremental

On a normal incremental run, applies append, delete/insert, or merge DML from a staged delta. Delete/insert removes matching keys or cursor ranges before inserting replacement rows. Cursor configuration controls replay bounds and may split work into microbatches.

```sql
MODEL (
  description "Example model",
  materialized incremental,
  incremental_strategy delete_insert,
  cursor activity_hour,
  cursor_type timestamp,
  cursor_grain hour,
  unique_key [activity_hour],
);
```

The first run, `--full-refresh` and a full `replay_on_change` rebuild build the whole table, as a table model does. A microbatch model instead drops the table and rebuilds it batch by batch.

See [Incremental](/docs/concepts/incremental) for cursor semantics, replay, schema changes, and microbatch execution.

## Snapshot

Maintains historical row versions with SCD Type 2 semantics:

```sql
MODEL (
  description "One row per customer",
  materialized snapshot,
  unique_key [customer_id],
  snapshot_strategy timestamp,
  updated_at updated_at,
);

SELECT customer_id, name, plan, status, updated_at
FROM __source("customers")
```

See [Snapshots](/docs/concepts/snapshots) for timestamp and check strategies, historical inputs, and full-refresh policies.

## Maintained

The warehouse keeps a maintained model up to date on a schedule you set, between builds. On Snowflake it is a dynamic table; a build creates it, changes it when its definition changes, and otherwise leaves the refreshing to Snowflake.

```sql
MODEL (
  description "One row per customer per order date",
  materialized maintained,
  refresh (lag 1h),
);

SELECT customer_id, CAST(ordered_at AS DATE) AS order_date, SUM(amount) AS revenue
FROM __ref("stg_orders")
GROUP BY customer_id, CAST(ordered_at AS DATE)
```

| Field | Default | Description |
|-------|---------|-------------|
| `refresh (lag <duration>)` | none | How far behind its inputs the model may fall: a fixed duration such as `5m`, `1h` or `1d`, at least `1m` on Snowflake. Without it, the model refreshes when a maintained model that reads it refreshes |
| `refresh_mode` | `incremental` | `incremental`, `full`, `auto` or `adaptive`. Snowflake rejects `incremental` for a query it can't refresh incrementally; use `full` for that query |
| `refresh_warehouse` | the connection's warehouse | Warehouse the scheduled refreshes run on |
| `refresh_on_build` | `false` | Refresh the model in every build that selects it, not only on its schedule |

Only Snowflake supports maintained models. See [Snowflake](/docs/concepts/adapters/snowflake#maintained-models) for the grants and change tracking they need.

### What the plan shows

| Change | Plan | What the build does |
|--------|------|---------------------|
| First build, or the dynamic table is missing | `create` | Creates it and fills it |
| Query or `refresh_mode` changed | `recreate, full recompute` | Replaces it; every row is computed again |
| `refresh` lag or `refresh_warehouse` differs from the warehouse | `change refresh settings in place` | Alters the schedule; rows stay |
| Nothing | `maintained` | Leaves it alone |

A model the plan keeps can carry one more line:

- `recomputes in full: stg_orders is rebuilt`: the build replaces a model it reads, so its next refresh computes every row again.
- `paused: scheduled refreshes are suspended`: Snowflake lists it as suspended, so it is not refreshing.

### During a build

A build pauses the maintained models it changes, and those that read a model it rebuilds, so they never refresh from half-built inputs. It resumes them when it ends, whether it succeeds or fails.

- Dynamic tables outside the project that read a paused model pause too, until the build resumes it. One that someone had suspended before stays suspended.
- A model that was already suspended when the build started stays suspended, and the build warns about it.
- If someone suspends a model during the build, the build's resume undoes that suspend.
- A kept model is refreshed during the build when a model built later in the same build reads it, so that model reads current rows. `refresh_on_build` refreshes it in every build.
- A target with `pause_maintained = true` leaves its maintained models suspended between builds and refreshes them only in builds; see [Targets](/docs/concepts/project-configuration#targets).

Two builds can't pause the same models at once. A build that needs a model another build holds fails with `A718`, naming that run. A build that stops without resuming, for example because its process was killed, leaves its models suspended. The next build that pauses maintained models on the target resumes them once that build has been silent for `[maintained] heartbeat_grace` (see [Maintained](/docs/concepts/project-configuration#maintained)). Until then, resume them in Snowflake by hand, or run `sqb build --ignore-maintained-grace` where the project allows it.

### Error codes

| Code | When | Fix |
|------|------|-----|
| `A013` | `materialized maintained` on an adapter other than Snowflake | Use `table` or `incremental` on that adapter |
| `A014` | `materialized materialized_view` on Snowflake | Use `materialized maintained` |
| `A015` | A `refresh` lag under `1m` on Snowflake | Set a lag of at least `1m` |
| `A016` | A model with no `refresh` that no maintained model reads, so it would never refresh | Add `refresh (lag 1h)` or another lag |
| `A716` | The adapter can't build a maintained model | Use an adapter that supports them |
| `A717` | No warehouse to refresh with | Set `refresh_warehouse`, or a `warehouse` on the connection |
| `A718` | Another build holds the models this build needs | Wait for it to finish, or for its hold to pass `heartbeat_grace` |
| `A719` | `--ignore-maintained-grace` without `allow_ignore_grace = true` | Set `[maintained] allow_ignore_grace = true`, or wait for the grace to pass |

### Limitations

- Writing out the default `refresh_mode incremental` changes the model's definition, so the next build recreates it once.
- A custom materialization named `maintained` is not used; the built-in one takes the name.
- Unit tests and scenarios treat a maintained model as a table.
- A snapshot rebuilt in full is created without change tracking. Before a maintained model reads it again, run `ALTER TABLE <snapshot> SET CHANGE_TRACKING = TRUE`.

## Custom

A project-local Python materialization can manage specialized persistence with adapter access, schema findings, query-change state, declared columns, and `ctx.run_audits`.

```sql
MODEL (
  description "One row per order",
  materialized partition_tracked,
  placeholders (
    partition_start "'2026-04-01'",
    partition_end "'2026-04-05'",
  ),
  config (
    tracking_table partition_state,
    partition_column order_date,
  ),
);

SELECT *
FROM __ref("stg_orders")
WHERE ordered_at >= @@@partition_start
  AND ordered_at < @@@partition_end
```

The `config` block is passed to the Python function through `ctx.config`. Runtime-owned `@@@placeholder` values remain unresolved until materialization execution.

The custom function owns staging, runtime type or contract enforcement, audit timing, promotion, and rollback. Framework final audits run after the function returns unless `MaterializationResult.audit_results` is populated. A custom materialization can call `ctx.run_audits` against a staging relation before applying changes and return those results through `MaterializationResult.audit_results`.

## When a build fails

| Materialization | What a failed build leaves |
|-----------------|----------------------------|
| View | The new view. Audits run after it is replaced. |
| Table (staged, the default) | The old table, untouched. Checks and audits run before it is replaced. |
| Table (`immediate`) | The new table. Audits run after it is replaced. |
| Incremental | The old table if a delta audit fails. Rows already written stay if a final audit or a later microbatch fails. |
| Microbatch full rebuild | A partly rebuilt table; the old one was dropped first. |
| Maintained | The created or altered dynamic table, resumed. Audits run after it changes. |
| Custom | Whatever the custom materialization does. |
