---
title: "Event Sinks"
description: "Export lifecycle facts and command output through project-owned providers."
---

Project event sinks live in `python/event_sinks/` and are imported from `sqlbuild.event_sinks`.
Each consumes one declared record type. Lifecycle and command-output streams remain separate
even when they share a provider and destination.

## Lifecycle event sink

```python
# python/event_sinks/publish.py
from python.providers.destination_client import DestinationClient
from sqlbuild.event_sinks import (
    LifecycleEvent,
    LifecycleEventKind,
    lifecycle_event_sink,
    lifecycle_event_to_json,
)


@lifecycle_event_sink(
    event_kinds={
        LifecycleEventKind.INVOCATION,
        LifecycleEventKind.RUN,
        LifecycleEventKind.RESOURCE,
        LifecycleEventKind.AUDIT,
    }
)
def publish_lifecycle(event: LifecycleEvent, destination_client: DestinationClient) -> None:
    destination_client.publish(
        route="sqlbuild.lifecycle.v2",
        key=event.invocation_id,
        payload=lifecycle_event_to_json(event).encode("utf-8"),
    )
```

Using `invocation_id` as a partition key keeps one invocation on one Kafka partition. Keep
`event_id` in the payload as the deduplication identity. Confirm the destination topic is not
compacted when complete lifecycle history must remain replayable.

### Invocation phases

Before a command runs its first node, it publishes one `invocation_phase` event (kind
`invocation`) as each step of its preparation finishes. The payload's `phase` names the step,
`duration_ms` says how long it took, and `count`, `name` and `detail` add what the step reports:

| `phase`          | When                                                    | Also carries                                                                  |
| ---------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `discovered`     | the project's declarations and Python were read         | `duration_ms`                                                                 |
| `compiled`       | the project compiled                                    | `duration_ms`                                                                 |
| `matched`        | a worker's compile matched its run's published snapshot | `duration_ms`                                                                 |
| `discovered_set` | a worker read a saved discovered set its run uses       | `name` (the set), `count` (items), `detail` (tags and when it was discovered) |
| `connected`      | warehouse connections opened                            | `duration_ms`, `name` (adapter), `count` (connections)                        |
| `inspected`      | the warehouse state the plan needs was read             | `duration_ms`                                                                 |
| `planned`        | the plan was generated                                  | `duration_ms`, `count` (nodes selected), `detail` (sub-steps)                 |

A run's page shows these steps in its events, and a "Preparing" bar before the first node on its
timeline. A consumer that doesn't know a `phase` can ignore the event.

## Command-output event sink

```python
from sqlbuild.event_sinks import CommandOutputRecord, command_output_event_sink, command_output_to_json


@command_output_event_sink(streams={"stdout", "stderr"})
def publish_output(record: CommandOutputRecord, destination_client: DestinationClient) -> None:
    destination_client.publish(
        route="sqlbuild.command_output.v1",
        key=record.record_id,
        payload=command_output_to_json(record).encode("utf-8"),
    )
```

Command output groups adjacent text into bounded byte chunks and flushes on elapsed time, stream
change, size, or close. A loss record reports bounded-queue drops. This stream is useful for remote
transcripts but is not lifecycle evidence.

A sink with a parameter annotated `sqlbuild.recall.RecallWriter` is not an ordinary sink: it
decides what [Recall](/docs/concepts/observability/recall#filtering-what-recall-stores) stores for
its stream.

## Configuration

Runtime configuration can narrow declaration filters:

```toml
[event_sinks.lifecycle]
event_kinds = ["run", "resource", "operation", "statement", "audit"]
min_severity = "info"

[event_sinks.lifecycle.named.publish_lifecycle]
event_kinds = ["resource", "statement"]
min_severity = "warning"
```

`shutdown_timeout` sets how long a command waits at exit for lifecycle sinks to drain queued
events. It is a fixed duration from `"0s"` to `"10m"`, defaults to `"2s"`, and is accepted only
under `[event_sinks.lifecycle]`, not per named sink. `"0s"` drops anything still queued at exit. The
final quarter of the budget is reserved for run and invocation outcomes: when it begins, other
queued events are dropped and counted so the outcomes still arrive. The setting does not change the one-second timeout for each sink call. A sink call still running when
the budget ends gets up to that one second to return before providers are torn down; teardown
always runs on the command's own thread. A cancel that leaves a step running skips teardown,
as described under [Providers](/docs/concepts/python-nodes/providers#lifecycle).

```toml
[event_sinks.lifecycle]
shutdown_timeout = "30s"
```

SQLBuild owns envelope validation, local queueing, filtering, and bounded dispatch. The project owns
destination credentials, serialization, routes/topics, acknowledgements, retries, retention, and
durability. SQLBuild core does not provide a Kafka or ClickHouse implementation.

## Delivery behavior

- `sqb compile` sends lifecycle sinks only its invocation start and outcome, never its
  `invocation_phase` steps or phase `operation` events, so a sink never lengthens a compile with
  phase deliveries. Other commands send every subscribed kind.
- Each sink receives events on its own long-lived delivery thread.
- An invocation's `invocation_started` arrives before its other events, and `invocation_completed`
  or `invocation_failed` after every other queued event. Events between them are prioritized:
  failures and terminal facts first, FIFO within equal priority. For exact chronology, sort by
  `invocation_sequence`.
- Queue overflow can displace or drop lower-priority records and is reflected in sink accounting.
  Run and invocation outcomes (`run_started`, `run_completed`, `run_failed`, `invocation_started`,
  `invocation_completed`, `invocation_failed`) are always admitted and never displaced.
- A failing or timed-out sink is isolated from command correctness.
- Each sink call has one second to return. When a call takes longer, the command prints
  `Warning: lifecycle sink '<name>' did not return from one call within 1s; its events are dropped until that call returns.`
  That call counts as failed and the sink's events are dropped and counted while it runs. Run and
  invocation outcomes are kept instead and delivered, with every later event, once the call returns.
  Time SQLBuild itself spends waiting for Python's GIL does not count against the call.
- `audit_completed` facts are published as each audit finishes (model audits in `sqb build` when
  their model finishes), not in one burst at the end of the run.
- When lifecycle events are dropped or fail, the command prints one warning to stderr with the
  counts and affected sinks, for example
  `Warning: command completed successfully, but lifecycle event export was incomplete: 140 of 248 events dropped, 0 failed (sink 'orders_events'). Check sink health: a sink call slower than 1s drops that sink's events until it returns; events still queued at exit need a longer event_sinks.lifecycle.shutdown_timeout.`
  A successful command then ends with
  `sqb audit completed successfully; only its lifecycle event export is affected.` The exit code
  and stdout, including `--json` output, are unchanged.
- When a sink provider's `teardown` raises, the same warning reports it with the provider and the
  error type, for example
  `sink provider teardown failed ('kafka' (KafkaProducer) raised KafkaException); events the provider still held may not have been delivered.`
  The error's message is not printed, because it can carry destination details. The exit code is
  unchanged. In a run, the warning appears with the run's output and events.
- Provider setup and declaration errors fail before execution because the project configuration is
  invalid.
- Providers shared by multiple sinks are set up and torn down once per command.

Use lifecycle facts—not command-output records—to build execution state and timelines.
