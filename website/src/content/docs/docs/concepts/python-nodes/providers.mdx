title: "Providers"
description: "Shared runtime services for Python nodes and hooks."

Providers are shared runtime services that SQLBuild discovers, configures, and injects into your Python nodes and hooks. Use them for external connections, API clients, or any stateful service that multiple nodes need access to.

## Defining a provider

Create a `provider.py` in a capability folder under `providers/` (see [Project layout](#project-layout)). A provider is a class that subclasses `Provider` from `sqlbuild.providers`:

```python
# providers/warehouse_client/provider.py
from sqlbuild.providers import Provider

class WarehouseClient(Provider):
    """Client for the reporting warehouse."""
    api_key: str
    endpoint: str = "https://api.example.com"

    def setup(self, ctx):
        self.session = create_session(self.api_key, self.endpoint)

    def teardown(self):
        self.session.close()
```

The class docstring is the provider's description and is required; a provider without one fails compilation with `P010` ([Descriptions](/docs/concepts/models/configuration#descriptions)).

`Provider` extends [pydantic-settings `BaseSettings`](https://docs.pydantic.dev/latest/concepts/pydantic_settings/), so provider fields are validated and can be populated from environment variables automatically.

## Provider name

Each provider has a runtime name used for injection. By default, the name is derived from the class name by converting to `lower_snake_case`:

- `WarehouseClient` becomes `warehouse_client`
- `SlackNotifier` becomes `slack_notifier`

Override the name explicitly with `provider_name`:

```python
class WarehouseClient(Provider):
    """Client for the reporting warehouse."""
    provider_name = "warehouse"
    api_key: str
```

Provider names must be valid Python identifiers (`lower_snake_case`). They share the global project resource namespace with models, sources, seeds, functions, loaders, tasks, assets, checks, and hooks.

## Using providers in Python nodes

Providers are injected into Python node functions by **parameter name**. Add a parameter whose name matches the provider's runtime name:

```python
from sqlbuild.tasks import task

@task
def export_orders(ctx, warehouse_client):
    """Export orders."""
    warehouse_client.session.upload(ctx.query("SELECT * FROM orders"))
```

SQLBuild matches the parameter name `warehouse_client` to the discovered provider with that name, sets it up if it hasn't been already, and passes it to the function.

You can also type-annotate the parameter for IDE support and compile-time validation:

```python
from sqlbuild.tasks import task
from providers.warehouse_client.provider import WarehouseClient

@task
def export_orders(ctx, warehouse_client: WarehouseClient):
    """Export orders."""
    warehouse_client.session.upload(ctx.query("SELECT * FROM orders"))
```

When a type annotation is present, SQLBuild validates that the discovered provider is an instance of the annotated class. A mismatch raises a compile-time error.

Provider injection works in all Python node types:

- **Loaders** (`@loader`)
- **Tasks** (`@task`)
- **Assets** (`@asset`)
- **Checks** (`@check`)

## Using providers in hooks

Python lifecycle hooks also support provider injection by parameter name:

```python
# hooks/python/notify.py
from sqlbuild.hooks import hook

@hook
def notify_complete(ctx, slack_notifier):
    """Notify complete."""
    slack_notifier.send(f"Model {ctx.model_name} built successfully")
```

```sql
MODEL (
  description "One row per order",
  materialized table,
  post_hooks [python("notify_complete")],
);
```

Providers are also available on the `HookContext` via `ctx.providers`:

```python
@hook
def notify_complete(ctx):
    """Notify complete."""
    notifier = ctx.providers.slack_notifier
    notifier.send(f"Model {ctx.model_name} built successfully")
```

## Using providers via context

All Python node contexts (`TaskContext`, `AssetContext`, `CheckContext`, `LoaderContext`) and `HookContext` expose a `ctx.providers` container for name-based access:

```python
@task
def export_orders(ctx):
    """Export orders."""
    client = ctx.providers.warehouse_client
    client.session.upload(ctx.query("SELECT * FROM orders"))
```

Both approaches (parameter injection and `ctx.providers`) are equivalent. Parameter injection is more explicit and enables type checking; `ctx.providers` is useful when provider access is conditional or dynamic.

## Lifecycle

Providers follow a lazy setup, reverse-teardown lifecycle scoped to the command invocation:

1. **Discovery** - on compile, SQLBuild discovers all `Provider` subclasses under `providers/` and validates their settings (from environment variables or field defaults). Missing [secrets](#secrets) follow the command's rules.
2. **Lazy setup** - the first time a provider is accessed during a build, SQLBuild reads its settings and calls `setup(ctx)`. Providers that are never used are never set up.
3. **Teardown** - after the command completes, `teardown()` is called on all providers that were set up, in reverse setup order. Teardown runs even if the build failed.

```python
class WarehouseClient(Provider):
    """Client for the reporting warehouse."""
    api_key: str

    def setup(self, ctx):
        # Called once, the first time any node accesses this provider
        self.connection = connect(self.api_key)

    def teardown(self):
        # Called after the command completes
        self.connection.close()
```

Both `setup` and `teardown` are optional. A provider with only field declarations and no lifecycle methods is valid; it acts as a validated configuration object.

### The setup context

`setup(ctx)` receives the active target's resolved settings as `ctx.target_config`, the same values Python nodes see (see [Target settings](/docs/concepts/python-nodes/overview#target-settings)):

```python
class PartnerStage(Provider):
    """Stage for partner exports."""

    def setup(self, ctx):
        target = ctx.target_config
        self.stage = f"{target.database}.{target.loader_schema}.partner_stage"
```

Which target `ctx.target_config` describes depends on what uses the provider:

| Used by | `ctx` |
| --- | --- |
| Python nodes in `sqb build`, `sqb check` and `sqb load` | The command's target |
| Event exporters and command output sinks | The command's target: `--target`, or the project's default target |
| Orchestration sensors | The target the sensor evaluates for |
| Orchestration calendars | `None` |

Details:

- When the project can't resolve the target's settings, for example because the target names a connection that isn't defined, every command that uses the target, such as `sqb build`, `sqb compile` or `sqb query`, fails before any exporter or sink provider is set up.
- Commands that don't use the target, such as `sqb format`, still run, and their exporter and sink providers get `ctx` set to `None`.
- In a project that defines providers, a sensor evaluation whose target's settings can't be resolved fails, and the sensor's cursor doesn't advance.
- Check for `None` in a provider that calendars, exporters or sinks use.

## Configuration from environment variables

Because `Provider` extends `pydantic-settings BaseSettings`, fields without defaults are read from environment variables. The environment variable name matches the field name in uppercase:

```python
class SlackNotifier(Provider):
    """Posts build notifications to a chat channel."""
    slack_token: str          # reads SLACK_TOKEN from environment
    channel: str = "#builds"  # has a default, environment variable is optional
```

Put local values in the project's `.env`, which every `sqb` command loads at start-up; variables
already in the environment win. See [Env file](/docs/concepts/project-configuration#env-file) for
another file per target or turning it off.

See the [pydantic-settings documentation](https://docs.pydantic.dev/latest/concepts/pydantic_settings/) for advanced configuration like custom env prefixes and nested settings.

## Secrets

Declare a secret as a field typed `SecretStr`. Laptops and CI jobs can then compile without production secrets, and builds check only the secrets their selection needs.

```python
from pydantic import SecretStr


class SlackAlerts(Provider):
    """Posts alerts to Slack."""

    channel: str = "#data-alerts"
    slack_webhook_url: SecretStr  # reads SLACK_WEBHOOK_URL
```

| Commands | When a required secret is unset |
| --- | --- |
| `compile`, `rules run`, `format`, `dag`, `lineage`, `scope` | Error `D012`, unless missing secrets are allowed |
| `build`, `load`, `check`, and runs on `sqb server` workers | Error before anything runs, only when a selected node or a sink uses the provider |
| `sqb debug` | Lists the missing secrets as warnings |
| `sqb location health` | Reports `missing_secrets` and exits `1` |

```text
$ sqb compile
error[D012]: provider 'slack_alerts' (providers/slack_alerts/provider.py) is missing secret SLACK_WEBHOOK_URL
  = help: set SLACK_WEBHOOK_URL, or pass --allow-missing-secrets where secrets aren't available
```

Allow missing secrets for the static commands in any of these ways:

| Where | Setting |
| --- | --- |
| Command line | `--allow-missing-secrets` |
| Environment | `SQLBUILD_ALLOW_MISSING_SECRETS=1` |
| `sqlbuild_local.toml` | `allow_missing_secrets = true` under `[settings]` |

The command then lists the providers it skipped on stderr, such as
`1 provider has missing secrets (allowed): slack_alerts`. Settings that aren't secrets are still
validated. Execution commands accept none of these.

```text
$ sqb build --select python/orders
error[D012]: selected nodes need secrets that are missing:
  slack_alerts  SLACK_WEBHOOK_URL  (partner_export_alert)
nothing was run
```

Run [`sqb debug`](/docs/cli/debug/) to see which secrets this machine has.

## Discovery rules

- Provider classes are discovered from `.py` files under `providers/` recursively
- Files named `__init__.py` or starting with `_` are skipped
- Each concrete (non-abstract) subclass of `Provider` is registered
- Provider names must be globally unique across project resources
- Settings are validated at discovery time. A missing or invalid setting that isn't a secret is a `D012` error; missing secrets follow [Secrets](#secrets)

## Plan output

When providers are used by Python nodes or hooks, `sqb plan` shows a Providers section listing each provider and its consumers:

```
Providers
  warehouse_client  2 nodes
  slack_notifier    1 node
```

Use `--verbose` to see which specific nodes consume each provider.

## Providers in the web UI

When a location publishes to [`sqb server`](/docs/cli/server/), the **Providers** page lists each
provider with its class and docstring. A provider's page shows:

| Tab | Shows |
| --- | --- |
| Settings | Each setting's type, environment variable and whether it is required; secret settings are marked, and flagged **missing** when the location's environment doesn't set them |
| Used by | The loaders, tasks, hooks and other code that take the provider, and the jobs that run that code |

Setting values, defaults included, are never published.

## Project layout

Give each provider its own folder under `providers/`, named for the capability it provides:

```
my-project/
  providers/
    warehouse_client/
      provider.py        # the Provider subclass
      constants.py
      _helpers/          # private to warehouse_client
    slack_notifier/
      provider.py
  hooks/
    sql/
      record_notification.sql
    python/
      notify.py
  python/
    orders/
      load_orders/
        node.py
        main.py
```

Discovery also accepts `.py` files directly in `providers/`. A project that selects the
[Python Rules](/docs/concepts/rules/python-rules#laying-out-providers) reports them, along with
anything else in a provider folder besides `provider.py`, its role files, `_helpers/` and
`_classes/`.
